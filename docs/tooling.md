# 仓库工具与验证

本库的本地检查选择、工具与报告格式由本文和现有检查目录拥有。旧可信执行与自动准入已退役，见[退役说明](admission-controller.md)。本地检查不发布 GitHub 准入结论。

完整 `all` 检查覆盖工具启动、源码身份、文档、技能成员与安装行为。成员和产品数量从清单推导；工具归属与消费者绑定由独立预期检查。[按需工具参考](../delivery/policy/tool-contracts.md)约束 Git、SSH、curl、jq 和 rg。

wechatide 的顶层及嵌套入口参与验证，但只安装顶层目录。执行器、安装诊断脚本及各自的离线测试参与门禁。门禁不调用真实 DevTools 或钥匙串。入口与具体行为见[使用指南](usage.md#微信项目配置devtools-初始化编译诊断预览项目列表自动化云开发与安装诊断)。

prose-check 是仓库自写的检查脚本，另有离线测试。它强制检查中西文之间的空格，对中文句长给出不阻塞的提示。它跳过标题、表格、引用、HTML 注释与代码块。缩进四格及以上只在列表之外算代码块。列表之内是嵌套或续行，那些行照常检查。它按空行合并折行再断句，跨行的一句按整句度量。它按读者所见计数，列表标记与强调符号不计入长度。`--fix` 只补空格，不改句长。超过 40 字的句子有可用标点边界时给出断点建议。它另有 `grades` 子命令，列举封闭集之外的分级词候选，只列举不判定。该子命令不参与门禁，供改动措辞规则后主动运行。

解析使用 CommonMark 语法树。哪一行属于哪种构造要看上下文，按行正则表达不了上下文。

修复位置取自 micromark 的记号流。语法树把解码后的字符摊平，不给逐字符的源码位置；记号流保留每一段的范围，实体与转义因此可修。少数实体解码出多个字符，那个文本节点整体不修。全角标点后的地址由树变换单独生成，没有源码位置。这一类同样整段不修。行内图片按分隔处理：它渲染出一个图形，两侧的文种已经分开。

GFM 的尾部标点裁剪只认 ASCII。中文句末的裸地址会把句号留在链接目标里。工具不管链接目标，这一条由作者自己看。

id-check 检查表格首列标识符。同一前缀的编号必须按出现顺序递增，标识符不得重复。跳号允许，回退不允许。默认形状可用 `--pattern` 替换。

两个检查器的源码都有运行时依赖。安装后的工具必须独立于仓库依赖运行，因此 `scripts/bundle-tools.ts` 把它们打包进 `delivery/tools/`。四项测试守住它：

- 产物等于当次构建
- 不含任何包导入
- 由源码实际加载的入口构建，不是 development 入口
- 脱离仓库运行时与源码结论一致

两者覆盖本仓库文档，在文档组里各占一项检查。它们读的源码清单与 markdownlint 同一份。prose-check 带 `--errors-only`，只列阻塞的空格错误；汇总行仍计入所有句长提示。id-check 不排除任何文件。调用方式写在[按需工具参考](../delivery/policy/tool-contracts.md)，它随部署发布；本页不发布。

两者都能用 `--version` 打印裸版本号。消费者按这个版本号固定工具。prose-check 另有 `--changed`。它只报告本次改动碰到的段落。报告也计数改动之外的发现。id-check 没有这个选项。顺序错误报在下降的那一行，限定范围会藏掉插入造成的缺陷。

gh 拥有通用 CLI/API/stack 调用合同，没有执行器。alibabacloud-find-skills 交付 curl/jq 消费绑定和完整资源，门禁不发起技能搜索、下载或安装。短信 Bash 工具及假 CLI 测试保留在技能目录；统一门禁调用测试、ShellCheck、三端官方技能验证器与完整成员检查，不新增真实云服务验证。完整工具身份与调用参考绑定见[绑定规则](#仓库登记维护)。当前交付状态与维护导航见 [README](../README.md#维护导航)。

任务临时目录入口的源码为 [task-temp.ts](../scripts/task-temp.ts)，打包到 `delivery/tools/task-temp.mjs` 并随各产品工具安装。[调用合同](../delivery/policy/tool-contracts.md#task-temp)约束前台执行、收尾及只读扫描。仓库回归覆盖成功与失败清理、中断保留、Git 与归属保护、链接边界，以及扫描不改写历史内容。无模型加载检查另核对工作区、临时目录、合并后清理和收尾四条入口链接。缺任一链接时失败；它只证明入口存在且进入提示，不证明语义完整或模型按时执行。这些检查也不证明历史目录已经可回收。该入口不安装自动清理配置。

## 准备工具

规则手工源与产品入口的分工见[交付架构](../README.md#规则与交付架构)。`bun run build:instructions` 从通用正文和三端适配生成原生入口；`build:install` 先执行这一步，再构建安装器。`Product instruction freshness` 门禁检查产物与源一致。不要手改生成入口，也不要单独对它们运行格式化。

宿主机需要 Bash、Git、jq、gh、curl。还需要 tar、unzip、Python 3.9 或更高版本。摘要工具可用 `sha256sum` 或 `shasum`。安装器不安装系统软件。它不修改 shell、个人代理或 agent 配置。归档测试还使用 `zip`。缺少必需工具会失败。

```bash
umask 077
bash scripts/install-tools.sh
.cache/agents-tools/bin/bun install --frozen-lockfile --ignore-scripts
.cache/agents-tools/bin/bun run build:install
```

Node 和 Bun 的版本由 [package.json](../package.json) 指定。[tool-versions.json](../scripts/tool-versions.json) 指定其他工具版本。它也固定平台、URL 和摘要。`verifiedAt` 是整个清单的上游核验基线日期。只有重新核验所有工具条目后才能更新。只更新单个工具时保留原日期。npm 依赖使用精确版本，并通过 [bun.lock](../bun.lock) 锁定。安装时禁用生命周期脚本。TypeScript 只做类型检查。固定 Node 直接执行维护脚本。

改动的源文件只要受 Prettier 支持，就运行以下入口。支持 Markdown 和 JavaScript。还支持 TypeScript、JSON 与 YAML。普通 Markdown 段落保持一段一行，使用 `--prose-wrap never`。其他排版采用默认值。生成文件只由生成器更新，不再运行 Prettier。上游原件遵循其保留约束。

生成器负责内容，Prettier 负责受支持文件的排版。依赖变更先由固定 Bun 更新 `bun.lock`，再按 JSONC 格式化。格式化不能替代依赖解析；完成后核对冻结安装仍接受该锁文件。

```bash
.cache/agents-tools/bin/bun run format <路径...>
.cache/agents-tools/bin/bun run format:check <路径...>
```

`format` 写回排版，`format:check` 只检查并通过退出码报告结果。两者传入同一批改动文件，不做全仓重排。格式检查独立于 `check.sh all`，完成改动时两者都运行。Prettier 处理源码排版。文档门禁阻塞混排空格和编号错误，并汇总句长提示。

本仓库是这些维护工具的第一个消费者。文档门禁检查全部 Markdown 的格式；手工源的链接在仓库位置检查，三份原生生成入口的链接由产品发布视图检查。安装回归在临时目标验证交付与恢复。Codex 加载检查用固定 CLI 的 `debug prompt-input` 回读临时 `CODEX_HOME` 中的完整指令和技能目录，并核对按需政策的交付字节。它不调用模型，也不证明模型遵守规则。dsh 与 Antigravity 的生成、安装和引用检查不等于原生会话已加载。提交钩子须配置 `core.hooksPath` 才会自动触发。

成员解析器计算当前清单的产品数量。`.cache/agents-build/` 只保留安装器产物。

安装器的构建命令生成 `.cache/agents-build/install.mjs`。它还生成 Zod、js-yaml 许可证 `install-licenses.txt`。工具安装器从同一已核验归档提取 Node 的唯一顶层许可证。它写到 `.cache/agents-tools/licenses/node-LICENSE`。完整门禁绑定这些文件与固定 Node，作为安装运行副本的输入。V9 安装计划在状态根的 `agents/install/<run-id>/` 保存候选和恢复运行副本，仅绑定显式选择的产品。V5/V6 保留 Codex 私有目录的原路径；V7/V8 沿用记录中的产品布局。门禁在临时目录重建并比对，也在脱离依赖的位置运行 bundle。缺失或过期失败。

安装器只把已验证的候选原子替换到 `.cache/agents-tools/bin/`。归档缓存每次重新校验摘要。随后它流式读取唯一的目标成员并检查版本。已有可执行文件不能仅凭版本输出绕过归档验证。损坏缓存、目录或链接目标、未知格式及版本不匹配都会失败。失败工具的旧目标保持原样。先前已成功准备的工具和有效下载缓存保留。

默认准备还包含[验证器清单](../scripts/skill-validator-versions.json)固定的上游 Python 原文件、PyYAML 与许可证。Codex 与 Anthropic 验证器保存在仓库私有缓存。每次离线检查从固定归档重建预期字节。它拒绝修改过的代码，也拒绝缺失或多余文件与链接。校验不信任可改写的缓存清单。准备过程会下载官方工具并执行版本探针。它不进行模型请求或个人安装。

## 技能格式校验

每项技能按清单中的产品集合运行对应官方验证器。`shared` 固定展开为 Codex 与 DeepSeek Harness (`dsh`)；新增产品由有序列表显式选择。成员解析器验证完整清单、顶层与嵌套归属以及元数据。所有嵌套入口随所属产品参与校验。安装和验证使用同一产品选择。

[适配器](../scripts/check-skills.ts)调用[固定上游执行入口](../scripts/skill-validator.py)。Codex 使用 OpenAI `codex` 仓库的 `skill-creator/scripts/quick_validate.py`；DeepSeek Harness (`dsh`) 复用固定上游 Agent Skills（Anthropic `skills` 仓库）的同名工具校验 `SKILL.md` frontmatter 与结构。版本、下载地址与 SHA-256 由验证器清单唯一维护。保留上游原字节与许可证，不修改校验规则来让候选通过。

`repository` 和 `all` 门禁分别登记各产品的校验结果与实际入口数量。任何验证器失败、缺失、损坏或覆盖不完整都阻断门禁。显式执行空选择同样失败。离线回归覆盖两套工具的真实正反例、共享与专用选择、嵌套入口以及缓存完整性。校验子进程使用临时 HOME，不传递模型凭据。

Antigravity CLI 的官方校验入口是 `agy plugin validate --strict --json`，见[插件文档](https://antigravity.google/docs/plugins)。固定版本为 1.4.12，由工具准备入口下载到仓库私有缓存。三个支持平台的归档先对照官方安装脚本所指 release manifest 的 SHA-512 核对，再把 SHA-256 固定在工具清单；保留原有全清单核验日期。准备过程只提取二进制并查询版本，不运行官方安装脚本，不修改个人 CLI。校验时把所选技能复制到临时插件目录，以最小 `plugin.json` 调用真实加载器校验。解析 JSON 后核对实际技能数量，并拒绝 error、warning 或不完整覆盖。此临时包装仅用于校验，交付仍是普通 Skills 目录。

三个产品的格式校验均进入统一门禁。Antigravity 回归使用官方二进制验证有效技能、缺失 frontmatter、名称不匹配与空选择。固定工具版本和实际二进制进入源码身份报告。官方插件校验不证明普通全局目录已被发现、模型会按需使用技能或外部服务操作可用；CLI 的 `/skills` 与 App 新会话的真实全局发现仍须在获准安装后分别核对。

Modern Web Guidance 的官方原件由[来源清单](../config/modern-web-guidance-source.json)逐文件校验字节及完整成员集。只有通过完整性检查的原件保留上游排版，不套用本仓库 Markdown、行文及表格编号风格。本地技能入口和调用合同仍接受全部文档检查；原件的相对引用、发布闭包和密钥筛查继续执行。修改、遗漏或额外加入原件均阻断校验。更新时运行[显式导入入口](../scripts/update-modern-web-guidance.ts)，以固定 npm 版本同步运行时和语料，不执行下载包。

各产品还分别检查完整发布引用。上游工具只校验其固定版本支持的技能格式，不证明完整客户端兼容性、加载或模型行为。新增产品字段时先核对上游支持范围。

## 选择检查

```bash
bash scripts/check.sh all
bash scripts/check.sh repository
bash scripts/check.sh ci
bash scripts/check.sh docs
bash scripts/check.sh docs markdown
bash scripts/check.sh docs links
```

| 选择 | 覆盖 |
| --- | --- |
| `repository` | 类型检查、安装器构建闭包、仓库回归、契约绑定与技能成员、各产品官方技能校验、能力层、发布形态引用、Codex 实际加载与密钥筛查 |
| `ci` | 原生工作流合同回归、Shell 语法、ShellCheck、actionlint 与 zizmor |
| `docs` | 文档 runner 回归、机器路径、显式 Markdown 文件列表、lint、离线链接与锚点 |
| `all` | 上述三组，每个登记检查执行一次 |

各产品交付内容直接保存在 `delivery/`，产品选择由交付模块拥有。发布形态引用检查按安装清单分别建立各产品的隔离目录，检查各自闭包内的链接。Codex 加载检查在相同形态下确认 CLI 会读到交付指令和技能目录。安装回归再验证文件与完整技能目录的替换和恢复。工具仍由固定 Bun 打包，产物的新鲜度由门禁检查。加载检查只证明 CLI 识别入口，不证明模型遵守规则或技能操作可用。产品行为场景的静态核对见[使用指南](usage.md#验证能说明什么)。

文档子选择器只缩小 lint 或链接检查的范围。文档 runner 回归仍会执行。因此两种子选择器都需要 Markdown 依赖和 Lychee。外部 URL 在离线链接检查中排除。不得据此判断远端内容可访问或正确。

开跑前，stderr 可能提示当前分支落后于 `origin/main`。这里的基准是本机上次取回的 ref。提示不进报告，也不影响退出码。每项检查只读一个快照。回退已合并决定的分支，在自身快照里仍可能自洽。不在仓库、没有远端 ref、与基相等或领先时一律沉默。它不 fetch，所以比较的是上次取回的结果。这个提示不是准入，不证明平台采用了 strict 同步策略；实际要求按[实例配置](review-gate.md#实例与证据边界)核对。

参数错误返回 2。缺少前置或检查失败时返回 1。子进程超时、收到信号、源码漂移或报告写入失败也返回 1。全部选中检查成功才返回 0。检查器保留完整子进程输出，每项报告只保留有界诊断摘要。单项检查有超时和输出上限。超限会终止其进程组并记录失败。

Node 测试由 [check-tests.ts](../scripts/check-tests.ts) 消费原生结构化事件。每个选中文件必须产生非空测试汇总，并收到最终汇总。失败、取消、跳过和 TODO 均使该项检查失败。空文件的进程退出码即使为零，也不算通过。测试输出仍由 Node 的 TAP reporter 呈现；控制台文字不能充当验收证据。统一门禁、CI 和提交入口沿用同一判定。

## 结果与身份

报告位置必须明确。父目录必须已存在且为物理路径。目标可位于仓库外，或仓库内已忽略的输出目录。它不得覆盖源码、工具与依赖目录、符号链接或其他用户的文件。

```bash
mkdir -p .cache/reports
bash scripts/check.sh all --report .cache/reports/check.json
```

报告采用 0600 权限原子写入。它记录实际选择、计划检查和逐项结果。工具版本、平台和源码身份也在其中。失败也保留已得到的观察。在模块加载之前失败时可能没有报告，CI 同样判为失败。

源码身份绑定四类文件：

- 当前存在的 Git 跟踪文件
- 非忽略未跟踪文件
- 实际使用的仓库工具
- 安装依赖的普通文件

执行涉及的目录也纳入被忽略文件。范围包括 `scripts/`、`tests/`、`delivery/policy/`、`config/`、`.githooks/`、全部技能资产和 CI 的 `.github/`。这样可避免工具读取未绑定输入。报告还绑定两端固定验证器代码和许可证。隔离依赖及其来源归档也在绑定范围内。命令使用包内真实入口。生成的 `node_modules/.bin` 链接不参与执行。普通源码或依赖中的其他链接和特殊文件拒绝接入。检查前后重新枚举并比较内容与权限。报告和 `.git` 不作为源文件。

这个身份记录受检内容与执行环境。它不能证明未来文件不会改变，也不授予安装或发布权限。不同平台的依赖与工具可能不同，不要求它们产生相同源码摘要。

## 上游内容维护架构

维护流程连接上游来源、本地能力、候选验证和产品安装。每周任务已接入 Modern Web Guidance 发布包、Rust API Guidelines 与 Microsoft Rust Guidelines 参考章节，以及属性测试技能，覆盖保留原件、参考评估及本地适配。现有执行入口见[官方内容自动更新](#官方内容自动更新)。其他来源按下述职责与实际消费者扩展。

### 维护对象与归属

上游来源与本地能力分别管理。一个来源可供多个技能使用；一个技能也可依赖多个来源。外部指南可用于维护政策，无须成为独立技能。候选选型由[来源登记](skill-sources.md#code-quality-maintenance)拥有，正式采用后才进入执行清单。

| 对象 | 唯一归属 | 边界 |
| --- | --- | --- |
| 上游来源 | 对应的来源锁与准备脚本 | 拥有来源身份、发布渠道、固定版本或提交、选中路径、摘要和许可证；不决定安装产品 |
| 本地能力 | `delivery/policy/`、`delivery/skills/` 及配套工具 | 拥有采用的行为、入口、引用、执行器和适配；外部原件与本地手工源分别维护 |
| 更新单元 | 来源准备器产生的有界候选 | 将必须兼容的来源、运行文件、引用和本地适配一起验证；独立结果分别交付 |
| 产品交付 | `config/personal-skills.txt`、`scripts/skills.ts`、`scripts/delivery.ts` | 拥有成员、产品与平台选择、完整引用和安装布局；不承担上游版本检测 |
| 检查与安装 | 现有检查器、安装器及回执 | 检查绑定候选字节；安装绑定产品目标，负责回读与恢复 |

职责扩展复用现有文件。来源锁保存机器事实；来源文档说明采纳理由、许可和差异。第二个来源接入时，只登记调度所需的来源标识及准备器关联。版本仍由各来源锁拥有。工具版本、官方验证器和应用内置资料继续保留原有权威记录。

### 三种更新方式

| 采用方式 | 自动准备的内容 | 合并前的采用判断 |
| --- | --- | --- |
| 保留原件 | 更新固定包或提交的选中原件、完整依赖与许可，生成来源锁差异 | 验证本地入口仍兼容；运行资产、索引和语料的配套版本一起更新 |
| 本地适配 | 比较旧上游、新上游和当前本地实现，提出完整差异 | 维护者完成语义合并，保留有效本地规则；未适配完的候选保持草稿 |
| 参考资料 | 比较已评估提交与新提交的相关章节，列出受影响本地政策 | 逐项决定采纳、保留原规则或无关；确认结论后更新已评估基线 |

直接改写上游文件的技能，在加入自动更新前保留可核验的旧上游基线和本地差异。复用外部原件的入口优先采用独立引用和本地包装。运行所需原件随能力交付；仅用于比较的基线放在明确排除安装的维护位置。导入时核对完整引用及许可，不复制整仓来替代依赖分析。

参考资料的更新可提出带固定提交、相关差异和政策映射的草稿 PR。候选中的基线变更只是提议；维护者完成影响判断后才合并。PR 保留采纳或不采纳的具体理由，主分支记录已完成评估的基线。无规则变更时也保留明确处置，避免把“检测到新提交”记为“已评估”。参考资料更新沿正常审查流程，不能因只改版本字段而套用依赖更新豁免。

本地原创技能按问题、接口变化和实际验收维护。例如 Sketch 应用内置指南继续由原生能力读取。应用随附的原件由获授权的宿主取得；GitHub 定时任务不声称能够检查本机应用。尚未采用的候选保留在选型文档中，不自动进入更新或安装。

### 准备与发布分离

来源准备器拥有来源特定的检测、下载、选择与完整性验证。npm 与 Git 来源分别使用各自的身份约束。来源变化、移动标签、缺失许可证、引用断裂或未知文件归属均停止相关候选。下载内容按数据检查；执行信任仍沿[不可信输入边界](../delivery/policy/tool-contracts.md#不可信输入的执行)判断。

准备结果绑定目标仓库、基准提交、更新单元、旧新来源身份以及准确增删文件。发布器复用固定仓库绑定、去重、并发检查、签名提交、未知写入回读和 PR 创建。发布器使用受信主分支中的准备器与归属规则。它重新核对允许路径和字节，拒绝计划扩大写入范围。涉及共享引用或同一来源基线的变更在一个兼容更新单元内完成。

待审单元不反复开新 PR。更高版本出现时等待当前单元处置，再从最新主分支生成候选。人工修改过的分支、已关闭 PR 和未知写入沿原对象恢复，不强推或重开。彼此独立的来源可分别更新。一个来源失败不阻止其他来源完成检测。整次运行仍报告失败及未完成项。

定时任务只准备候选和创建 PR。语义适配由获授权的维护者完成；代码与安全审查、CI 和合并继续使用[仓库流程](review-gate.md)。合并后的本机更新由获授权宿主调用现有安装器。定时任务不获得个人配置、产品安装或其他主机的操作权限。

### 状态与验收

区分上游检测到的版本、PR 提议的版本、主分支采用的版本和各产品实际安装状态。工作流和 PR 保留检测结果与候选处置。主分支的来源锁与政策定义采用状态。安装计划和回执定义安装状态。参考资料另以已评估基线表示评估进度。复用这些记录，不另建全局状态账本。

| 验收范围 | 证据 |
| --- | --- |
| 来源与更新 | 固定身份、完整引用、许可、旧新字节、增删边界；无变化、来源漂移和下载失败分别处理 |
| 本地适配 | 本地规则与接口保留，冲突得到处置；参考变更有明确政策映射和采用结论 |
| 发布 | 无重复 PR，不覆盖人工提交；基线竞争、历史 PR 和未知写入有有界恢复 |
| 产品能力 | 既有格式、引用、构建与安装检查；行为或工具接口变化时增加相应真实调用和新会话验收 |
| 交付收尾 | 当前候选通过审查与 CI；合并和安装分别回读；临时资源按原有规则清理，恢复材料保留 |

机械模拟、新会话行为、线上 PR 创建和本机安装分别报告。只有结构检查通过的技能不能标为实测通过。尚未发布新版本时，保留线上创建更新 PR 未验证的边界，不伪造上游发布。

### 实施顺序

按完整结果接入来源。已有消费者与剩余扩展分别列明；该顺序不自动授权全部候选安装。

| 阶段 | 可验收结果 | 必要变化 |
| --- | --- | --- |
| 已有基础 | Modern Web Guidance 更新 PR 和三端交付 | 保留现有来源准备、每周任务、审查及安装流程 |
| 首个 Git 来源 | Rust API Guidelines 到现有 `rust.md` 的更新与评估 | 来源锁、固定章节、Git 准备器、草稿 PR 与评估检查同属一个消费者；继续复用产品安装与公共发布器 |
| 第二个 Rust 参考 | Microsoft 指南补齐安全、FFI、feature 与性能建议 | 两个参考来源共用获取与评估实现，分别锁定章节并创建更新 PR；同一政策变化后重新核对两份评估 |
| 首个适配技能 | Trail of Bits 属性测试到三端技能，并用于安装记录摘要测试 | 保留七份原件和完整许可，绑定本地七份文件与逐项适配结论；更新候选保持草稿，复用 Git 获取与公共发布器 |
| 专项审查与页面验收 | Rust 风险模式和 Web 质量测量各自交付完整技能 | 共用来源校验与更新适配器，分别保留许可、误报边界、实际消费者和新会话验收 |
| 后续来源 | Web、小程序等实际选定项沿同一职责接入 | 按来源与消费者补充准备及验收；复用稳定部分，不预建通用插件平台 |

## 官方内容自动更新

本节描述已实现的六个来源。职责划分见[上游内容维护架构](#上游内容维护架构)。

[upstream 工作流](../.github/workflows/upstream.yml)每周一 UTC 02:17（北京时间 10:17）检查已采用来源，也支持从 `main` 手动运行。矩阵独立处理六个来源，关闭 fail-fast。一个来源失败不取消其他来源，运行仍保留失败结果。[调度入口](../scripts/upstream-pr.ts)仅接受固定来源名；准备步骤不传入发布令牌。

Modern Web 的 npm 准备器完整更新 CLI、索引、指南和许可证。两个 Rust 参考、属性测试、Rust 专项审查与 Web 质量审查复用 [Git 获取器](../scripts/upstream-git.ts)，固定仓库身份、前向提交和已选文件，核对 Git blob 与文件摘要。下载内容不执行。[Modern Web 适配器](../scripts/upstream-modern-web.ts)、[Rust 参考适配器](../scripts/upstream-reference.ts)与[技能适配器](../scripts/upstream-adapted.ts)分别产生受限变更，再交给[公共发布器](../scripts/upstream-publish.ts)。Microsoft 的固定来源与章节由[来源模块](../scripts/microsoft-rust-source.ts)拥有。

无相关更新时不创建分支或空 PR。每个来源版本使用独立分支；同版本已有任何状态的 PR 时不再创建。同一来源已有其他版本待审时先等待。遗留分支、基线变化或写入结果未知均停止，由维护者核对原对象后恢复。自动化不覆盖人工提交、不重开已关闭 PR、不强推，也不自动合并或安装。

本仓库的 `GITHUB_TOKEN` 是此工作流专用的机器人身份例外，仅允许固定仓库内创建受管更新分支、签名提交及 PR。交互式 `gh` 的人类身份合同保持有效。工作流只在发布步骤传入令牌；回读签名、父提交、完整变更字节及 PR 目标。未获信任的新上游执行器只作为数据进入 PR，后续验证沿现有隔离 CI 和审查边界。

启用时由获授权的配置所有者打开仓库 Actions 创建 PR 所需设置，保留默认只读令牌权限及既有保护。GitHub 将创建 PR 与批准 PR 合并在同一设置中；本工作流不调用批准接口。默认令牌创建的 PR 可能要求维护者先批准运行 CI，见 [GitHub 说明](https://docs.github.com/en/actions/concepts/security/github_token)。随后按[仓库审查流程](review-gate.md)完成检查、独立审查、发现处置和获授权合并。指南与执行器更新不属于仅版本清单的审查豁免。

首次真实运行区分“官方当前无更新”与“已创建更新 PR”。本地模拟覆盖新版本、并发变化、历史 PR、未知写入和回读失败；没有官方新发布时，不伪造版本或制造空 PR 来声称线上写入已验证。35 MiB 的请求大小限制是本发布器的防护，并非 GitHub 平台容量承诺。超限时停止，不拆成半完成提交。

### Rust API Guidelines 评估

[来源锁](../config/rust-api-guidelines-source.json)中的 `revision` 表示候选原件提交，`assessment.revision` 表示已评估提交。自动准备保留旧评估，因此草稿 PR 的当前来源检查预期失败。不得靠删除检查、伪造结论或标记 ready 绕过评估。

本流程也适用于 [Microsoft 来源锁](../config/microsoft-rust-source.json)，其范围为六个映射章节与 MIT 许可证。两个来源分别创建草稿，但都绑定同一 `rust.md`。修改政策后须对照两组已采用章节重新评估，再更新各自摘要；不能只重算摘要掩盖语义冲突。无关章节更新不会自动扩大采用范围。

1. 核对 PR 的固定上游比较链接、变更原件和许可。范围是命名、类型安全、灵活性、互操作性四章及两份许可证。准备器的章节映射指向受影响 `rust.md` 段落。
2. 对照现有政策，决定采纳、保留或不适用。只实施已确定的本地规则变化；保留项目采用范围、业务值类型与调用方控制等既有边界。
3. 将 `rust.md` 的已评估引用更新到该上游提交。编辑来源锁的 `assessment`，填写同一提交、每个选中输入的明确结论及理由，并绑定最终政策的 SHA-256。无规则变化时仍说明原因。
4. 运行 `.cache/agents-tools/bin/node scripts/rust-api-source.ts --check` 与 `.cache/agents-tools/bin/node scripts/microsoft-rust-source.ts --check`，再执行本节约定的完整门禁。政策的任意后续编辑都会使旧摘要失效；原件变更不能沿用旧提交的评估。
5. 完成评估后将草稿标记 ready，按正常代码审查、所需安全审查、CI 和获授权合并执行。合并后从受检版本更新本机并回读；评估原件不安装到产品目录。

政策摘要可用以下只读命令计算。写回评估仍是维护者明确完成的动作。

```bash
.cache/agents-tools/bin/node --input-type=module -e 'import {readFileSync} from "node:fs"; import {digest} from "./scripts/rust-api-source.ts"; console.log(digest(readFileSync("delivery/policy/rust.md")));'
```

### 适配技能更新

[共用来源校验器](../scripts/adapted-source.ts)与[更新适配器](../scripts/upstream-adapted.ts)服务属性测试、Rust 专项审查与 Web 质量审查三个实际消费者。各来源模块独立固定仓库、原件、许可、本地完整文件集和分支前缀；同一上游仓库的计划也不能互换。下述适配步骤同时适用三个技能，明确采用范围后才能扩大输入清单。

[Rust 专项审查来源锁](../config/rust-risk-source.json)采用七份独立检测提示及许可，交付短入口、三份引用和完整许可。未采用上游入口、命名代理、脚本或其他检测器；这不是完整 rust-review 包。逐项核对取消语义、线程与 lifetime 约束、panic/ABI、外部资源上限及路径竞态的前提，保留反例与证据缺口。新提示不会因上游新增而自动加入技能。校验命令为 `.cache/agents-tools/bin/node scripts/rust-risk-source.ts --check`。

[Web 质量审查来源锁](../config/web-audit-source.json)绑定 Addy Osmani 的审查入口、测量引用及完整 MIT 许可。该社区来源不是 Google 官方产品。原件中的五个类别技能与分析脚本不在采用范围，本地入口改用实际可用的浏览器能力及已有 Modern Web Guidance；三份原件完整保留用于比较。更新时核对真实用户数据、实验室测量、渲染观察与源码假设的区别，以及私有页面、状态保持、只读边界和不适用的部署规则。校验命令为 `.cache/agents-tools/bin/node scripts/web-audit-source.ts --check`。维护记录须绑定全部四份交付文件；来源内容更新不等于测量方法已经适配。

### 属性测试技能适配

[来源锁](../config/property-testing-source.json)绑定 Trail of Bits 仓库身份、`main` 提交、入口、五份引用和许可证。`revision` 表示候选原件；`adaptation.revision` 及本地七份文件摘要表示已完成适配。自动更新只改维护原件和来源锁，保留旧适配记录；草稿候选在适配前不能通过当前来源检查。

1. 对照旧原件、新原件及当前技能，核对全部变更与 CC-BY-SA-4.0 许可。引用目录新增文件、缺失许可或特殊文件会停止准备，须先由维护者明确完整引用与许可范围。
2. 按实际语义合并入口及五份引用，保留独立性质、项目测试库选择、只读审查、执行界限与宿主清理责任。原件位于 `config/upstream/property-based-testing/`，不作为技能入口执行或安装。
3. 更新入口中的固定来源链接和完整许可证，再在来源锁填写同一 `adaptation.revision`、七份本地文件的 SHA-256 及每个输入的采用结论与理由。不改变本地建议时也说明保留理由，不能只重算摘要来替代适配。
4. 运行 `.cache/agents-tools/bin/node scripts/property-testing-source.ts --check` 和完整门禁。行为变化另做真实新会话验收；结构检查只能验证文件、摘要及记录一致，不能证明语义结论正确。
5. 完成适配后标记 ready，沿正常审查、CI、获授权合并和安装流程交付。安装完整本地技能及许可，不安装比较原件、上游评测执行器或插件注册文件。

## CI 与审查边界

原生 [checks](../.github/workflows/check.yml) 监听发往 `main` 的 `pull_request` 和 `main` push。PR 事件包括 opened、synchronize、reopened、ready_for_review 和 edited。草稿及元数据编辑也执行两个平台，没有路径或 job 条件跳过。PR 检查本次平台 merge SHA；push 检查本次 push SHA。checkout 固定为 `github.sha`，Action 使用完整 commit pin，并关闭凭据持久化。

两个结果名称为 `repository (ubuntu-latest)` 和 `repository (macos-latest)`。每个平台完整准备工具、冻结安装依赖、构建安装器，再执行 `all --report .cache/reports/check.json`。每个写入步骤设置 `umask 077`，Bash 使用失败退出和 pipefail。矩阵关闭 fail-fast，一个平台失败不会取消另一个。每 job 超时 30 分钟，不启用缓存。日志记录实际 runner 系统、架构、checkout SHA 和 PR head/base。

检查工作流只声明 `contents: read`，在 GitHub 托管 runner 执行，不使用 secrets。并发按 workflow、事件和 PR 编号或 ref 分组，新运行取消同组旧运行。main push 按 ref 检查最新状态，不保证被后续 push 替代的历史提交完成检查。被取消的运行保留 cancelled 结论，不计为通过。关闭 PR 不新建源码检查，在途任务可自然结束。取消、失败、超时和等待平台批准均不是成功。合并冲突与 fork 批准等待也不构成已验收结果。

[关闭后锁定](../.github/workflows/lock-pr.yml)独立监听 `pull_request_target: closed`，覆盖关闭和合并。它使用默认分支的 workflow，不 checkout 或执行候选代码。任务只声明 `pull-requests: write`，使用本次 `GITHUB_TOKEN` 调用 GitHub API，不使用 PAT 或仓库 secret。执行前读取原 PR，已重开或已锁定就跳过；写入后回读锁定状态。写入报错也先回读，不重发，未确认锁定则任务失败。同一 PR 的重复事件串行处理，不取消在途写入。PR 在读取和锁定之间被重开仍有竞争窗口，自动锁定也有事件处理延迟。owner 和合作者仍可评论；此入口不解锁重开的 PR，不归档或关闭 PR，也不限制 open PR 的外部评论。历史批量锁定属于单独的平台操作，不由该事件入口扫描补做。

Actions 日志与 job 结论提供托管结果。JSON 报告仅供诊断，不是认证凭证；准备失败可能没有报告，job 仍失败。actionlint 检查工作流及内嵌 Shell，zizmor 检查权限等静态风险；项目回归用现有 js-yaml 解析事件、矩阵、权限和完整命令合同。它们不证明真实平台已执行。工作流注册、两平台运行和 required 配置均按[实例与证据边界](review-gate.md#实例与证据边界)验收，不沿用旧仓库结果。

正式代码与安全审查由仓库外的提供方执行。按[使用指南](usage.md#验证能说明什么)核对提供方、候选、实际报告和发现处置。按[项目约定](review-gate.md#原生-ci-与独立审查)选择提供方，消费所选提供方的实际报告。本地检查或 CI 通过不替代独立审查。

当前合并要求由[项目约定](review-gate.md#重建期交付规则)拥有。旧实现保存在 Git 历史，运行原件与未知操作仍按原身份恢复。源码删除不证明旧外部操作已经终结，也不授权重复发送。

## 仓库登记维护

本节只供仓库维护，不随公共工具契约发布。安装后的调用者按需读取[工具约束](../delivery/policy/tool-contracts.md)。

| 清单 | 职责 |
| --- | --- |
| [inventory](../config/tool-inventory.txt) | 盘点已交付的 subject、领域和工具类别 |
| [owner 索引](../config/tool-contracts.txt) | 每个 subject 对应唯一手工契约或保留的固定执行器 |
| [consumer bindings](../config/tool-bindings.txt) | 指明消费者通过读取、直接执行或 wrapper 使用哪个 owner |

三份文件使用各自版本头及固定列数的 TAB 行。未知列、重复项、未知 subject、缺失 owner 均失败。空集合和不一致引用也失败。当前只登记 core，根检查器拒绝 `network/` 路径。网络能力尚未交付，未来接入须有领域验证器。

绑定完整性覆盖已登记 subject 的可变生产消费者声明，独立预期清单核对当前消费者集合。脚本与可变工作流必须在首个执行语句之前声明约束（先读 owner，再用工具），检查器对声明与绑定做双向核对。已登记的 Markdown 消费文件从候选技能目录独立枚举全部 Markdown 及技能 `scripts/` 中已交付的 Bash、MJS、CJS 执行文件；测试替身不作为生产消费者。

声明约束维护及调用前的阅读，不声称运行时执行了 Markdown。按摘要固定的执行器登记自有 subject 和完整执行能力，内部工具使用由对应摘要与测试覆盖。

[gh 技能](../delivery/skills/gh/SKILL.md)拥有 `gh`、`github-api` 与 `gh-stack` 的通用调用合同。检查器自身的 gh 版本探针绑定到 gh 技能。

执行工具的版本探针同样属于消费者使用。安装入口选择的固定工具及启动器的实际探针均完整登记。检查器也登记其直接执行的探针。只读取依赖清单里的版本字段不算执行该工具。

调用已登记的 `enforced-wrapper` 时，消费者必须绑定其 subject。subject 由该 wrapper 声明。包装内部的非探针辅助工具由被委托执行器绑定。调用方不递归复制绑定。例如安装入口的 curl 使用由工具启动器登记。这个边界不免除调用方自己直接执行的工具和上述版本探针。

Markdown owner 使用独立正文段落中的 `Contract subject:` 标记。代码示例、引用块和 HTML 注释不算定义。标记后必须有实际规则正文。脚本 owner 在首个执行语句之前使用对应注释。代码也必须落实其边界。固定执行器采用显式 SHA-256。仍有消费者的执行器保留准确字节和测试，已退役入口不继续登记。

`read-before-use` 首次使用时，必须先链接 owner。链接位于同一正文段落或列表项中。之后再出现 `Use tool` 与 subject 的明确调用标记。代码块、引用块和 HTML 注释中的使用标记不算声明。非执行示例应在代码块、引用块或 HTML 注释内。不能用普通正文冒充声明。消费者就是 owner 时，定义和本段规则提供直接归属。`enforced-wrapper` 除头部声明外，还必须匹配已交付 wrapper 的执行行。只有注释、打印或示例中的路径无效。新增工作流时再按其实际调用维护相应回归。

[检查器](../scripts/check-tool-contracts.ts)使用固定 markdownlint 的 token API 检查本仓库的 owner、声明与路由，通用 Markdown 由库解析，实际消费者的独立预期来自验证测试。[归属与加载场景](../tests/scenarios/rules.md#归属与加载-fixture)覆盖对应预期，不读取个人 HOME。

结构检查不证明规则语义完整、没有冲突或模型会遵守指令。工具打包产物的新鲜度由构建闭包检查；直接维护的规则源由必需成员检查核对是否存在。语义遗漏仍由行为场景与审查识别。历史旧值保留在原记录中，不因与现值不同而失败。

## 提交入口

[pre-commit](../.githooks/pre-commit) 只调用仓库固定 Node 与统一检查入口。运行前必须准备上述固定工具和冻结依赖；入口不自动改写现有 `core.hooksPath`。

可选择 `docs` 的条件有四个：

- 集合非空
- 完全暂存
- 没有其他未跟踪或未暂存改动
- 全为普通文档

结构检查必需文件和契约路径即使是 Markdown，也选择 `all`。这里的契约路径指 owner 与 consumer。下列改动同样选择 `all`：

- 源码、指令、policy、技能
- 可执行文件、重命名、删除
- 部分暂存及无法确认的排除清单
- `docs/usage.md` 的操作合同。安装测试从中独立推导目标预期，改动后运行完整检查。

Git 读取失败直接拒绝。

选择器读取 Git 交给 hook 的索引。它清除 Git 的仓库局部环境，然后启动检查。这样可防止临时索引或仓库位置泄漏到测试。`all` 检查工作树。部分暂存或路径提交时，不得把该结果说成提交索引的内容证明。临时仓库回归实际触发普通、`-a`、路径及替代索引提交。受控失败 gate 必须拒绝提交。暂存内容、HEAD 和配置均必须保留。单独运行 hook 不改写索引字节。这些测试不在主工作区创建提交或配置 hook。

选择完成后，固定 Node 用 `process.execve` 将自身替换为统一 Shell 入口。信号、每项超时及子进程清理由既有检查器负责。hook 不再留下额外的等待父进程。该入口使用本仓库固定的 Node。它覆盖 macOS 与 Linux，未提供 Windows 适配。
