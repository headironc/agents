### Wechatide installer disposition

The four upstream modules are **inspected inputs, not adopted code**. Every wechatide slice so far has adopted semantics and recorded that the upstream files are protocol evidence rather than code, because this skill ships no license file and, as recorded for the initial unit and for initializer, its original licensing terms remain unverified. The two skills that do carry upstream code, openai-docs and gh, each retain the upstream Apache-2.0 license; wechatide has nothing equivalent. Copying these modules would be this repository's first adoption of wechatide code under an unverified license, so the diagnosis is written here instead. The Human chose that disposition when the slice was proposed.

There is also a functional reason. Upstream's checker accepts any `wechatide` on PATH that answers `-h`, while the [call executor](../delivery/skills/wechatide/scripts/call.sh) additionally requires the resolved command to sit inside an application bundle and refuses anything else as `cli-unbound`. A copied checker would not answer the question this delivery's own executor asks.

| Input responsibility | Disposition and reason |
| --- | --- |
| Installation state and compatibility | Adopt the decision sequence as semantics and re-derive it for macOS in the repository's own [installation check](../delivery/skills/wechatide/skills/installer/scripts/check-install.mjs): locate the bundle, reject the NW.js marker, read the Electron package version, compare it with the threshold, then resolve the CLI. Upstream's Windows registry probing is not reproduced, because this delivery is macOS-only and reports any other platform the way the executor does. |
| The compatibility threshold | Do not hard-code upstream's value as authoritative. The check reads `MIN_COMPATIBLE_VERSION` out of the installed module when one is present and reports `minimumVersionSource: installed`; with no installation to read it falls back to the recorded `2.02.2607152` and reports `recorded`, so a stale repository value is visible in the result rather than silently applied. |
| Divergent installations | Report `cli_other_install` rather than a compatible verdict when the inspected root and the bundle PATH resolves into are different. Runtime and version come from the inspected root while the executor runs whatever PATH finds, so a compatible answer there would describe a bundle the call never uses; that case has no executor refusal, because the call can succeed against the other installation. The two roots are compared by device and inode rather than by text, since the caller's spelling and the canonical PATH target differ under casing on a case-insensitive volume, a symlinked component or a firmlink, and a text comparison reported those as split installations. |
