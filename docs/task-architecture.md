# 目标、授权与任务协作架构

本文提出 Goal、附加审批策略与任务协作的职责划分。目标是减少实例信息混入长期文本，同时保留完整业务结果、准确授权和未决责任。方案复用已有政策、项目合同和执行材料，不增加调度框架、常设台账或固定聊天层级。

本文保存架构与验收设计，运行要求以链接的权威政策为准。Goal 与附加策略的内容归属和语义继承已落实到[正文与动作绑定规则](../delivery/policy/models.md#goal-and-authorization-content)及其所属章节；其余建议另按[切片与持续交付边界](../delivery/AGENTS.md#implementation-slices)选择。文档合并、规则实施、安装、客户端加载和实际行为分别验收。阅读或采用本文不产生 Goal 创建、配置修改、发布或部署权限。

## 现状与问题归属

原 [Goal 规则](../delivery/policy/models.md#goals)中持续责任的例外容易将具体实例重新带入目标；附加策略也缺少明确的正文边界。这两项已由上述内容规则补齐。[策略接续规则](../delivery/policy/models.md#automatic-review-policy-succession)继续拥有原授权核对、完整替换、共享配置保护、字段级写入及读回。

[委派规则](../delivery/policy/models.md#delegation-and-acceptance)已要求直接交换、独立工作并行、及时消费就绪结果及复用有效证据。执行中出现纯中继、无依赖等待或重复验证时，先纠正执行。只有规则确有缺口，才修改唯一权威源。

[接班规则](../delivery/policy/models.md#lead-succession)另有持续协调的硬时间上限。这是待调整的规则选择，不能作为普通执行偏差处理。阶段职责、额外验收轮次及供应商配额要求，则按项目采用范围判断。

## 内容归属

| 内容 | 回答的问题 | 保留的内容 | 不承担的内容 |
| --- | --- | --- | --- |
| Goal | 最终完成什么，怎样算完成？ | 业务结果、范围、验收、稳定约束、排除及完成条件 | 进度、排期、当前执行实例与操作授权 |
| `auto_review.extra_policy` | 原授权允许什么，受什么限制？ | 项目目标、动作类别、条件、排除及停止条件 | 新授权、进度账本与调度脚本 |
| 项目合同 | 该项目怎样判断结果及交付？ | 业务规则、验收覆盖、阶段责任与交付条件 | 临时队列、当前负责人和运行句柄 |
| 技能与工具合同 | 某项能力怎样调用和恢复？ | 输入输出、资源边界、错误处理、读回与重试规则 | 当前业务排期及额外业务权限 |
| 现有执行材料 | 谁推进哪个候选，下一步是什么？ | 聊天与写区归属、候选、依赖、槽位、句柄及未决责任 | 第二份业务规则或授权来源 |
| 原始证据 | 实际执行了什么，结果是什么？ | 原始 Human 指令、实际输入输出、候选绑定、结果和限制 | 由摘要推导的新授权或新验收结论 |

原始授权仍由 Human 指令拥有。附加策略只表达其有效含义；具体动作材料提供原文定位及对象映射。项目合同、Goal 和策略不能相互生成权限。实例信息迁出正文后，继续留在已有聊天、任务、PR 或原始报告中，不新建平行登记系统。

### 内容归属判据

稳定边界、运行实例、单对象或单次授权，以及原文与动作映射的要求，统一见[正文与动作绑定规则](../delivery/policy/models.md#goal-and-authorization-content)。对应正反例见[稳定正文与精确授权场景](../tests/scenarios/rules.md#稳定正文与精确授权)。

### Goal 的行文与继承

[Goal 规则](../delivery/policy/models.md#goals)拥有结果、验收、语义完整继承及接口限制；历史整理、暂停和未知操作责任的验收见 [Goal 接续场景](../tests/scenarios/rules.md#goal-接续与吸收新指示)。

### 附加策略的行文与适用范围

[策略接续规则](../delivery/policy/models.md#automatic-review-policy-succession)拥有正文结构、完整替换和更新后的验证。准确授权映射复用上述共同边界；真实配置迁移仍是独立操作。

## 协作与验收

### 职责与聊天

明确采用总协调时，协调者承担分解、依赖、资源冲突、推进和组合接纳。任务或领域负责人承担业务判断和实质验收。作者持续负责实现与片内修复；独立验收者执行要求中的独立检查。职责分开不意味着必须建立四层聊天。

独立且承担长期交付责任的任务，沿[既有选路规则](../delivery/policy/models.md#task-start-and-execution-routing)使用可见持久聊天。已获授权的短辅助工作可用子代理，结果返回原 owner。普通短任务留在当前聊天。子代理活动是否可见，与能否承担完整持久交付责任分别判断。

作者与验收者直接交换稳定候选、发现及补验结果。协调者接收最终结果和需要协调的问题，不转发每轮普通交流。收到 ready 结果后，及时接纳、指出具体缺口或安排下一授权动作。持续作者保留修复责任，避免每轮重新派发竞争写者。

### 并行与证据复用

一树一写者及候选绑定继续有效。共享工具的排他使用由对应能力合同和项目采用规则拥有。只串行化真正争用资源或依赖前序结果的动作。离线准备、独立检查、CI 和组合准备在输入允许时并行。

串行合并不要求全部开发串行。是否等待取决于该动作需要的业务不变量、源输入或集成条件。就绪结果按真实条件推进；正在运行或结果未知的操作保留原句柄与观察者。

复用输入未变的证据。候选或基线变化后，补齐受影响覆盖，并保留项目要求的完整门禁。通用[发现处置规则](../delivery/policy/review.md#findings-and-disposition)要求无未解决阻断项及完整处置，不要求没有历史发现或没有建议。项目明确采用更严格条件时，改变条件属于项目决策。

Nucleus 的阶段优化归该项目负责。配额检查、`PASS` 且 `0 findings`、原生阶段和一键脚本等要求，由项目核对采用范围。不将项目专项条件搬入通用默认，也不以通用规则为由自行取消。两次原生操作看似相同，不证明其责任、输入或验收覆盖相同。

### 状态检查与接班

建议将持续协调的硬时间上限另片改为状态检查和实际限制触发。检查协调者能否准确定位当前 owner、候选、有效约束、下一动作及原操作。状态清楚时继续原职责；出现混淆、重复核验或运行限制时，及时准备恢复或安全接班。

同一目标下，可先使用受支持的上下文压缩。目标分叉时再评估 fork。压缩不转移责任，fork 不证明上下文已经清空。具体机制仍受接口、授权和运行条件约束。

保留[现有接班的责任转移要求](../delivery/policy/models.md#lead-succession)。旧协调暂停新派发，继任者核材料并接受，旧协调确认停止后，新协调才派发。活动任务和未知操作沿原 owner 继续，不要求全部操作结束才交接。无法接任时报告具体缺口，不把时间经过当作转权或完成。

在相应规则正式修改或有效 Human 指令明确调整前，现行时间要求仍有效。普通试用不默默停用该要求。

## 共享配置与安装

### 附加策略更新

复用[策略接续合同](../delivery/policy/models.md#automatic-review-policy-succession)。获准更新后，读取完整当前字段、有效配置层及版本。保留其他项目仍有效的授权和限制，准备可审查的完整替换及变化说明。原值保存在可恢复位置，不放入一次性 scratch。

使用实际支持的字段级接口，并在可用时使用版本检查。并发变化先重读和协调；未知写入先读回同一目标。不修改未授权的主审批模板、阈值、沙箱或其他配置。没有合适接口时保留具体限制，继续独立工作。

分别验证字段已保存、目标聊天采用的配置、具体 reviewer 的实际输入和该次判定。受管覆盖及模板支持各自核对。字段保存或聊天创建不证明审批器收到文本；无法核对时保持未知，不制造外部写入探针。

### 源码、安装与生效

仓库源码、受检候选、安装目标及运行会话是不同对象。部分安装只证明所选目标。安装报告即使绑定最新源码，也不证明未选成员已经同步。沿[安装合同](usage.md#产品选择与安装)回读准确产品、目标和实际字节。最近一次安装的 commit 不代表整个环境。

当任务要求合并后部署最新 `main`，部署 owner 在合并确认后刷新目标 ref。绑定包含已合并变更的最新提交，验证该候选，再生成并执行正式安装计划。若部署前 `main` 又变化，重新判断并验证新输入。报告具体部署版本及核实时点，不宣称此后永远最新。

安装范围来自当次授权。完整同步某个产品时，核对该产品的完整交付目标；部分安装则如实标明部分。其他产品、个人配置和清单外文件保留各自边界。共享安装目标保持一个执行者；已有部署运行时沿原结果协调，不启动竞争安装。

安装器回读、客户端加载及真实行为分别验收。运行中的聊天不假定热加载。架构文档的合并与安装，也不会自动实施本文提出的规则修改。

## 修改归属与实施切片

| 权威位置 | 处理建议 | 保留或排除 |
| --- | --- | --- |
| `models.md` 的 Goals | 明确正文归属和语义继承，收紧实例例外 | 保留创建权、完整结果、暂停及未决责任 |
| 同文件的策略接续 | 补充行文边界和精确授权映射 | 复用完整替换、字段级更新、并发保护及读回 |
| 同文件的委派与连续性 | 复用现有责任和证据规则，纠正执行偏差 | 不叠加同义规则或固定审查轮次 |
| 同文件的 Lead succession | 单独评估状态检查替代硬时限 | 保留唯一接责、原操作和归档条件 |
| `review.md` | 复用覆盖、处置和验证复用要求 | 项目专属验收条件由项目决定 |
| `writing.md` | 复用单一 owner、稳定引用及去重复要求 | Goal 和策略语义不在此复制一份 |
| 协调启动模板 | 缩回输入、分工、可选授权及导航 | 项目内容有明确接收 owner 后再迁出 |
| 行为场景 | 随选定规则切片更新现有预期 | 提案场景不冒充现行规则或实测结果 |

首个内容规则切片处理了 Goal 与附加策略的内容归属和语义继承，并同步导航、模板引用和[相关场景](../tests/scenarios/rules.md#goal-接续与吸收新指示)。它要求运行实例变化时正文保持稳定，同时准确恢复约束、暂停和未决责任。规则源码存在不证明实际 Goal 或共享配置已迁移。

硬时间接班另成独立切片。项目阶段优化由项目 owner 处理。实际 Goal 或共享配置迁移另按有效授权执行。先保存原材料和限制，再迁移内容，最后核语义与读回。缺少授权、接口或原文只阻塞依赖动作，不丢弃原有责任。

不新增通用调度器、自然语言授权解析器或实例登记框架。也不靠禁止 UUID、路径或数字的词法检查来证明语义正确。

## 可逆试用与验收场景

首次执行试用保留原阶段责任、配额要求及全部验收覆盖。先观察及时交槽、槽外并行、直接交换、紧凑观察和候选语义核对。存储 Goal 与共享配置保持原状。改变原生阶段责任、`0 findings` 条件或配额频率时，先由对应 owner 明确处理原有要求，再试用变更。

使用一个自然推进的完整切片观察执行，再利用实际发生的恢复或交接验证连续性。未发生的场景保留未验证，不为测试制造外部写入、取消运行或额外聊天。结果写入已有任务材料，保留真实候选及限制。不建立统计台账，也不从阶段 token 占比推导节省比例。

下表是方案验收设计，尚未证明模型实际遵循。规则实施时，对照[既有行为场景](../tests/scenarios/rules.md#goal-接续与吸收新指示)合并重复预期。

| 场景 | 可观察的通过条件 | 失败判据 |
| --- | --- | --- |
| 聊天、写树或候选变化 | 正文稳定，动作准确绑定新对象 | 改实例就重写目标，或复用旧候选证据 |
| 单对象或单次授权 | 原文及动作映射仍限定对象和次数 | 抽象后变成同类持续权限 |
| 目标含过期进度和未知操作 | 目标保留结果与余责，句柄及 owner 可追溯 | 逐字复制历史，或删掉未知操作责任 |
| 发布暂停且修复仍获授权 | 发布停止，独立修复继续 | 接班恢复暂停阶段，或扩大为全停 |
| Goal 正文无法修改 | 保留有效补充及接口限制 | 假完成、改数据库或缩水腾位 |
| 独立候选 ready | 及时接纳或返回具体缺口 | 等待无关 CI、重复派工或增加写者 |
| 共享 Sketch 槽位占用 | 其他离线工作继续，调用保持单槽 | 将槽位等待扩成全部工作等待 |
| 候选局部修复 | 补验受影响部分，保留必需完整门禁 | 重跑全部未变证据，或删减覆盖 |
| 并发策略更新 | 冲突后重读，保留其他项目有效条款 | 覆盖并发值或丢弃范围限制 |
| 配置写入结果未知 | 先读回原目标，加载未知如实报告 | 盲目重放或用保存证明实际加载 |
| 状态清楚或出现实际混淆 | 在调整后的接班规则下分别继续或安全接班 | 为计时造接班，或失真后继续竞争派发 |
| 仅安装部分目标 | 报告实际目标及未覆盖成员 | 用最新来源 commit 宣称全环境同步 |
| 合并后部署最新 main | 刷新、验证并安装准确最新候选 | 安装旧 PR 快照或仅凭源码合并宣称生效 |

文档方案执行文档门禁。改变规则行为的后续切片执行完整 `all` 门禁及适用场景核对。真实模型演练另核模型、材料和操作授权。无模型 loader 只证明入口与文件可用，不证明模型读取按需正文或遵循语义。[工具说明](tooling.md#选择检查)维护具体检查入口。

## 官方资料与推论边界

- [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex) 说明持续目标、可核验终点及约束。本文据此采用紧凑目标表达；具体归属和授权要求仍是本仓库方案。
- [Multi-agent](https://developers.openai.com/api/docs/guides/responses-multi-agent) 说明独立工作适合并行，也指出共享可变资源和串行链的限制。这不证明某种聊天层级固定最优。
- [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) 说明当前客户端可展示子代理活动。活动可见不单独建立持久交付能力或独立判断。
- [上下文管理建议](https://developers.openai.com/blog/mastering-codex-remote-for-engineering#7-manage-context-before-it-becomes-a-problem)建议同目标压缩、方向分叉时 fork。该文没有为本仓库的硬时间接班上限提供依据。
- [配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)说明附加策略与活动 policy 一起应用，以及受管 `guardian_extra_policy` 的优先级。它不证明某个本地审批器已加载候选文本。
