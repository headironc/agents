# 能力配置

这一类发布的全是**推荐值**。`codex.toml` 与 `rust-lints.toml` 都是给你合并进自己配置的文本。本仓库不写任何产品配置文件，也不写消费项目的 `Cargo.toml`。

理由是所有权。产品配置是你的文件，里面有与规则无关的个人内容。覆盖它会出事。所以这里只发布可比对的文本，合并由你做一次。

## 安装

把 `codex.toml` 的内容并进 `${CODEX_HOME:-$HOME/.codex}/config.toml`。`rust-lints.toml` 合并进采用 `policy/rust.md` 的项目的 Cargo.toml。

## 推荐值

`codex.toml` 里的两项保持注释，展示与[操作边界](../AGENTS.md#operation-boundaries)相配的可选设置。仅安装这个片段不会改变个人配置。

`sandbox_mode` 与 `approval_policy` 对应操作边界。`workspace-write` 实测过四格。工作目录内的写入落盘。目录外的同一条写入报只读，文件不落盘。同一条写入在 `read-only` 下同样被拒，所以第一格的成功来自这个设置。而目录外的读取成功。所以它管写不管读。`on-request` 表示外部动作前请求人确认的形态。推荐理由是这个形状与操作边界同形，不是任何越界率数字。本仓库没有测过它，采用与否由你判断。

## 规则与执行配置

规则的预期行为由 [Rust 规范](../policy/rust.md)定义。`rust-lints.toml` 提供其中可机械判定部分的执行配置。规范保留要求，配置拥有启用方式，两者职责不同。测试从要求推导预期，验证执行器的行为。消费者未启用配置时，已采用的要求仍然适用。此时存在执行缺口，不能声称工具已经强制。

里面每一条都在真实工具链上看着它让一个违规 crate 失败过。对照是同一份代码、不带配置。写进去却判不了任何东西的条目不该留。两条这样的条目已移出，并写明了原因。

维护配置时还要验证符合要求的输入能通过。只看违规输入失败，无法排除执行器拒绝所有输入。工具漏报或误报时，按规范核对并修正执行边界。不能用当前工具的输出反向改写要求。
