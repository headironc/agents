# Model selection

This policy owns task organization, model and execution-route selection, chats, workspaces, Goals, collaboration, and continuity through acceptance, succession, and task closure. Project adoption follows the [rule ownership requirements](../AGENTS.md#code-preferences).

## Stable principles

- Select a model by the business judgment, responsibility boundaries, impact, and uncertainty the work involves. File counts and lines of code do not measure that burden.
- For complex work, prefer one task or domain lead continuously responsible for understanding the business, designing responsibilities, settling key judgments, and accepting the result. That lead can delegate complete implementation while retaining those responsibilities. An explicitly adopted overall coordinator has the separate coordination role below.
- Apply model selection to both the lead agent and delegated tasks. It does not require creating subagents or building a scheduling framework. Choose within the tools and delegation authority actually available.
- Follow explicit user model choices, applicable project overrides, and higher-priority instructions. The defaults below do not override them.

## Task start and execution routing

Establish the intended outcome, current slice, authoritative sources, effective Human authorization, and any existing division of responsibility. Reuse a clear assignment and valid evidence. A self-contained question or ordinary short task can be completed in the current chat; it does not require a new chat, Goal, workspace, or preliminary Astra stage. For work that needs organization, make the following choices before creating or dispatching the corresponding chat and before taking on the whole implementation. Revisit only choices affected by changed scope or material inputs.

When an overall-coordinator arrangement is explicitly adopted, the overall coordinator performs coordination only: task decomposition and dispatch, dependency and integration order, follow-up, arranging acceptance, and handoff. Assign business investigation, architecture, implementation, repairs, and substantive acceptance to the responsible task or domain leads. The coordinator can verify delivery bindings and evidence completeness and arrange business acceptance; it does not take business design or code implementation back from those owners. References below to a lead's business judgments, design, implementation, or substantive acceptance mean the responsible task or domain lead. This division does not require an extra coordination layer for ordinary tasks.

Select the responsible role and [model](#current-defaults) separately from the client, receiving service, execution mechanism, and execution host, applying [runtime limits](#runtime-limits) to the actual invocation. Use Astra High for complex investigation, architecture, and key acceptance judgments under the responsible task or domain lead. Once the design and slice are clear, use the effective Human division of work to hand the complete implementation, checks, and repairs to a separate Sol High chat when that arrangement is authorized. The Astra task or domain lead retains design and acceptance; ordinary implementation choices remain with Sol. Apply [escalation](#escalation) when implementation reveals a new business, authorization, transaction, or recovery judgment, continuing unaffected work while that lead resolves it.

Choose the execution host by the task's suitable existing candidate, required toolchain, and actual resources. Each owner completes the assigned implementation, validation, signing, publication, and repairs from a suitable workspace within effective authorization, using the project's normal Git, PR, and CI flow. The chat or coordinator's host does not determine the execution host: a local chat can operate the existing remote workspace through supported tools. Local work can independently complete a slice using a suitable local repository. Coordinate routine cross-host integration through identified Git revisions and their evidence; do not use archives or copies of uncommitted source as the normal integration or acceptance path. Apply the [workspace default](#workspaces) when starting independent source-development work in a new chat. Beyond that preparation, do not move source, patches, dependencies, or artifacts between hosts, or create another checkout, solely to change roles, models, or chats or use spare compute. Available compute alone does not justify relocation; neither local nor remote execution has unconditional priority.

Choose between the current chat, an authorized internal subagent, a visible independent chat, and [Claude Code with DeepSeek](#claude-code-and-deepseek-delegation) by the complete result, acceptance needs, available tools, and cost of splitting a cohesive responsibility. Actively assess the Claude Code route at this decision point, including complete implementation, rather than after completing all execution yourself. A visible-chat request requires a visible chat; an internal subagent does not substitute for it. Create chats only under effective Human authorization, reusing a covered batch grant. Use the [delegation contract](#delegation-and-acceptance) for binding, original authorization, writer ownership, result delivery, and acceptance.

For design-draft creation and iteration, use the Codex model and effort in [current defaults](#current-defaults), honoring an explicit Human choice under [runtime limits](#runtime-limits). Apply the existing [design workflow](../skills/figma-design-workflow/SKILL.md) for editable results, critique, and pixel acceptance. Choose Figma when the task needs it; a local editable preview can satisfy a design task whose required output allows it. Claude Code with DeepSeek and the Design plugin are optional routes under effective Human choices, not prerequisites for producing a draft. Terra can assist with reference-image understanding and draft inspection; the lead retains product and interaction judgments and final acceptance. For browser or desktop interface operation, default to Terra under the model table and runtime limits. Prefer a suitable connector or API when available; a model preference does not require using a GUI.

Before execution, settle the applicable [chat and workspace binding](#workspaces) and whether an authorized [Goal](#goals) is appropriate. The recipient verifies the original requirements, design, execution binding, permitted operations, and acceptance conditions before dependent work. Proceed autonomously through the selected slice and its repairs under the existing [implementation rules](../AGENTS.md#implementation-slices). Route a ready result and the original owner's next authorized action promptly through the existing [acceptance and follow-up rules](#delegation-and-acceptance), including notifying or waking that owner when action is ready. Use those rules to distinguish actual dependencies or running operations from actionable work instead of leaving a ready task idle. Asynchronous observation, review, succession, and archival retain their existing owners below. A turn ending alone does not complete the responsibility.

## Current defaults

These are maintained usage defaults, not official capability guarantees or proof that a model is available. Keep the mapping here so model updates do not duplicate or redefine the stable principles.

| Work | Preference | Model identifier | Reasoning effort |
| --- | --- | --- | --- |
| Complex business rules, responsibility design, and core authorization, transaction, concurrency, or recovery boundaries | Astra High | `gpt-6-astra` | `high` |
| Specific rule conflicts, major design tradeoffs, or difficult defects that remain unresolved after gathering the relevant evidence | Astra Extra High | `gpt-6-astra` | `xhigh` |
| Ordinary implementation under a confirmed design and established patterns | Sol High | `gpt-6.1-sol` | `high` |
| Design-draft creation and iteration | Sol Max | `gpt-6.1-sol` | `max` |
| Mechanical work with clear boundaries and readily checkable results | Luna High, optional | `gpt-6-luna` | `high` |
| Browser and desktop interface operation | Terra | `gpt-6.1-terra` | Select a supported effort for the task |
| Reference-image understanding and design-draft inspection assisting the design workflow | Terra, supporting role | `gpt-6.1-terra` | Select a supported effort for the task |

The design-draft preference applies to producing and refining design artifacts; ordinary product-code implementation keeps its own default. The Terra preferences follow the Human's workflow choice and the [official visual and computer-use positioning](https://learn.chatgpt.com/docs/models); they are not evidence of local design quality or end-to-end operation. Terra assistance preserves the selected design route and lead acceptance and does not expand permission to operate apps, create chats, or create Goals.

## Escalation

- Move a Luna task to Sol High when it requires understanding a call chain or affects behavior in multiple places. Move it directly to Astra High when it involves key business or responsibility judgments.
- Move a Sol task to Astra High when it introduces a judgment about fact ownership, state rules, authorization order, transaction boundaries, or recovery responsibility. Resolve that judgment before extending implementation that depends on it.
- At Astra High, first gather the authoritative rules and trace the actual call chain. If rules still conflict, a major tradeoff remains unresolved, failures remain unexplained, or repairs of the same failure class repeatedly fail, identify the specific contradiction or evidence gap before moving to Extra High. Reconsider the underlying assumptions instead of repeating them with more reasoning. Return to the regular effort once the issue is clarified.
- Ask the Human for missing business decisions. Escalation neither supplies those decisions nor expands the [implementation slice](../AGENTS.md#implementation-slices) or [operation authority](../AGENTS.md#operation-boundaries).

## Runtime limits

Use only models, reasoning levels, and switching mechanisms the actual tool interface supports. Before creating, continuing, or changing a chat, select for the destination's assigned result and map the selected, authorized model and effort to the supported invocation parameters. A model choice for generating a design draft does not automatically cover a separate rule-maintenance or product-implementation chat. Inspect the interface's conditions for overriding defaults first. When an override requires an explicit Human model choice, identify that original choice and its scope. Reuse an explicitly adopted ongoing mapping that specifies the model for this role while its scope and the interface's conditions still apply; a tool requiring a choice in the current message retains that narrower condition. A general repository preference or an agent-authored role prompt does not establish an explicit Human choice. When the conditions are unmet, preserve the required default and report the difference rather than claiming the selected model was requested.

During the existing dispatch and reception checks, verify the emitted parameters and available supported readback. Distinguish the requested model and effort, client-saved chat settings, the active turn's model and effort, and server execution identity and effort. A success receipt containing only a chat ID establishes neither saved settings nor an active-turn switch. Report only the unverified layer as unknown; role text, model self-description, or a client selection does not prove server identity. Unknown server identity does not excuse omitting permitted parameters. A continuation request does not prove an in-progress turn changed unless the interface guarantees that behavior or trusted turn metadata verifies it. Reuse unchanged invocation and readback evidence under the existing [check rules](review.md#checks).

Use an available, authorized mechanism to take back or reassign an escalated task. If the main session cannot switch, or the selected model or effort is unavailable, report the limitation and any verified runtime identity. Request user action only when continuation actually depends on it. Otherwise continue the work supported by the available environment and existing authority, stating any fallback without silently replacing an explicit user choice. While a necessary decision or switch is pending, continue unaffected work.

Apply authorized per-call or per-chat model choices through supported parameters; distinguish those choices from persistent personal or global configuration changes, which retain their own authorization boundary. Do not automatically change persistent configuration or expand tool permissions to satisfy a model preference. Preserve tool refusals and higher-priority restrictions. Model selection does not grant access to a model, a service, or additional operations. Product controls are described in the [official OpenAI model documentation](https://learn.chatgpt.com/docs/models); verify what the current environment actually exposes.

## Workspaces

Bind source work to the task's actual repository directory on the selected execution host, or its confirmed working directory when the work has no Git repository. Where the client exposes Project grouping, select the corresponding existing Project and verify its repository or directory; a Project name alone does not bind execution. A client without Project grouping can start directly in the correct directory. If no suitable project or repository exists and establishing one is necessary, ask the Human whether to establish it. Non-Git work does not require creating a Git repository.

Default a new Git source-development chat to one independent worktree for its assigned implementation. Prefer the client's managed worktree mechanism; use a native Git worktree when that mechanism is actually unavailable under the support checks below. Inspect the chat's existing binding first and reuse a suitable worktree already provisioned for it. A clean main checkout alone is not a reason to skip this default. Necessary worktrees inside an existing repository are ordinary authorized preparation, without a separate business decision for each one.

Continue an existing chat in its verified suitable workspace, including an existing main-checkout binding; this default does not require migration on resumption. Read-only work can inspect the existing candidate without owning another implementation worktree. Non-Git work uses its confirmed directory. An explicit Human workspace choice or a concrete client constraint can require a different arrangement; identify the applicable exception and preserve actual refusals. When the default cannot be established, continue independent preparation and resolve the specific binding gap before dependent implementation. Inspect changes, their value and ownership, and active operations before using any workspace. Preserve useful WIP under its owner and isolate work when sharing would interfere. Remove disposable changes only under effective cleanup authorization after verifying their scope and recovery requirements; calling changes useless does not authorize discarding another task's work.

Limit each chat to one owned source-implementation worktree, whether managed or native. At the first implementation turn, on resumption, and before allocating another checkout, verify the chat's existing binding from its available attachments, actual Git worktree state, and task history. Count a worktree provisioned by the client before the first model turn as the chat's existing worktree. Reuse an existing binding; do not create successive worktrees for separate implementation purposes in the same chat or use a clone or copied implementation checkout to evade the limit. When a second independent implementation worktree is necessary, assign it to a separately authorized chat and verify that chat's actual binding before work starts. Restore the same worktree through its supported recovery path when needed. Restoring that binding does not allocate a second implementation workspace. Disposable Git fixtures created and cleaned entirely by a foreground test do not count toward this limit; do not use that exception for implementation checkouts. If the required chat or workspace mechanism is unavailable, report the specific gap and continue independent preparation rather than creating an unowned second worktree.

Design, implementation, and acceptance can use the same suitable checkout in stages. The per-chat limit does not require a distinct checkout for each role. Before transferring a write stage, verify the actual candidate and WIP, account for in-flight or unknown operations under their existing handles and owners, and obtain the receiving writer's acceptance. The outgoing writer stops writing before the recipient starts. Read-only inspection does not transfer writer ownership; unchanged ownership needs no repeated handoff. Coordinate acceptance and checks against a stable candidate so they do not race source edits. Reuse valid evidence under the [check rules](review.md#checks); a role or chat change alone does not require reconstructing the candidate or rerunning checks. Isolate when concurrent writes, useful unrelated WIP, or actual client constraints prevent safe sharing.

When the selected host lacks a validation dependency, first identify the uncovered checks and the project's supported execution path. Keep implementation and delivery with their assigned owners; bind any separate validation to the actual candidate and preserve required coverage of the integrated behavior. A missing local dependency alone does not make relocation of uncommitted implementation necessary. When a concrete capability, platform, or resource constraint does require relocation, explain why the normal development and validation paths cannot satisfy it and apply the existing candidate, WIP, writer-acceptance, and execution-binding requirements. Preserve original operation handles, unknown outcomes, and permission boundaries. Normal Git fetch and publication, actual source inspection, formal review, and necessary recovery preservation remain available within effective authorization; they do not require a new approval for each transfer.

For the new-chat default or necessary isolation, reuse a suitable worktree owned by the chat or create one for the intended repository and verified baseline. Check whether the actual client, repository, and session operation support a managed worktree. Shared access does not transfer a managed attachment or make another chat's checkout attachable. Verify the supported attachment and lifecycle operations before relying on such a transfer. An absent MCP tool alone does not establish lack of client support. When the managed mechanism is actually unavailable, state the concrete reason before using a native Git worktree within the existing preparation authority. Preserve actual refusals under the [operation boundaries](../AGENTS.md#operation-boundaries).

Apply the single [execution context contract](tool-contracts.md#执行上下文) before editing or validating, including the actual chat directory, tool target, candidate, and applicable Project grouping. For a managed worktree, wait for creation and registration and read back the attachment. For a native Git worktree, verify its actual Git worktree binding without claiming a managed attachment. A requested mode, ordinary clone, success receipt, or matching HEAD alone does not prove the binding. If necessary isolation remains unavailable, identify that concrete gap and continue independent preparation; do not create a workspace in the wrong repository or change client configuration to simulate support. Preserve existing WIP and active operations under their current owner. Move existing work only at a safe handoff, with its inputs and outstanding operations accounted for and the new binding verified.

Keep acceptance originals and required ignored recovery material outside a disposable checkout, or copy and verify them there before retirement. Follow the [completion and archival requirements](#task-completion-and-chat-archival) before retiring the worktree or archiving its chat. The [official worktree documentation](https://learn.chatgpt.com/docs/environments/git-worktrees#worktree-cleanup) describes automatic cleanup, including on chat archival and under the configured retention limit. Inspect actual results; do not assume that keeping a chat retains its checkout indefinitely. This policy does not authorize changing those settings.

## Task temporary directories

Keep disposable command output under one private allocation with a traceable task or chat owner and a stated purpose. Reuse that allocation for the same foreground operation instead of scattering scratch directories. Read the [temporary-directory tool contract](tool-contracts.md#task-temp). Use tool `task-temp` for foreground commands that support its scratch environment and await all descendants. Keep Git worktrees under the existing workspace lifecycle, and keep shared caches with their capability owner. For tools with their own temporary-resource lifecycle, use their supported cleanup and verify its result rather than nesting a second owner around them.

Keep acceptance originals, recovery snapshots, and diagnostics that must survive outside disposable scratch before cleanup. A known foreground exit permits the wrapper to clean only its newly created allocation under the command's effective preparation and cleanup authority. An interruption, unknown external operation, background process, or ownership change requires owner verification; ending a wait or observing an absent PID does not establish termination. Preserve retained allocation paths and the specific remaining condition in the existing task result, without a separate ledger.

At task closeout, account for temporary resources created by that task alongside the existing worktree checks: verify removal, or state the owner, retention reason, and next condition for cleanup. Use the read-only scan to locate leftovers after interrupted execution. Existing unmarked directories remain unknown; age, naming, or an idle chat does not authorize deletion. Do not retrofit ownership markers onto historical directories to make them eligible for automatic removal. Periodic deletion and historical cleanup require their own effective scope and authority.

Inspect the command's cleanup result when it exits, before treating its temporary resources as settled. On resumption after interruption, resolve the recorded allocation, original operation, and retained condition before reusing or replacing the scratch directory. Inspect the known allocation first; use a bounded read-only scan only when its location is missing. If the temporary-directory tool is unavailable, report the missing delivery and use an existing project-owned lifecycle with equivalent ownership and cleanup when available. Otherwise continue work that does not depend on allocating scratch; do not silently scatter unowned directories or install personal configuration.

## Goals

Create a Goal only when sustained pursuit is appropriate and the Human or applicable higher-priority instructions explicitly authorize Goal creation for that outcome and chat. A complex task, a new chat, an assignment to keep working, or another chat's Goal alone supplies no creation authority. Without it, continue the authorized task normally. A Goal records the intended outcome, acceptance criteria, scope, key constraints, exclusions, and completion conditions; keep progress, logs, operation handles, and evidence in existing task material. A Goal does not grant publication, merge, deployment, or additional scope.

During formal succession for the same business objective, verify the original explicit Goal-creation authorization, its effective coverage of the successor chat or collaborating role, and the successor's actual Goal state. When that authority still covers the successor and `get_goal` returns `null`, reuse it to create the full Goal without asking for the same approval again. Authorization limited to the original chat, an uncovered role, or a different objective does not authorize creation in the successor; continue independent authorized work normally.

Create the chat and Goal as separate operations through the [supported Goal interfaces](#goal-tool-interfaces), then read back the complete effective Goal and compare it with the authorized source. A creation receipt or summary does not establish the effective text. Preserve an existing unfinished Goal and its owner; do not mark it complete to make room for another one.

When new instructions affect the objective or a constraint, reconcile the latest effective instructions with the full outcome, acceptance, exclusions, repairs, and remaining responsibility. Treat superseded implementation choices as retired, and preserve responsibility for their historical effects and unresolved operations. Use a supported amendment or safe continuation or handoff under existing authorization; preserve the interface limitation when text or status cannot be changed. Do not recreate a narrower objective, modify a status database, or claim completion to bypass that limitation. A paused publication stage does not end independent local work that remains authorized. Follow [continuity](#continuity-and-evidence) and [completion](#task-completion-and-chat-archival) for actual responsibility transfer and termination.

### Goal tool interfaces

Check the actual interface before calling it. Currently, `create_thread` has no Goal parameter. Verify chat creation and its actual target before using `create_goal` in the chat covered by explicit creation authorization. Put the full objective in `objective`; set `token_budget` only when explicitly requested. An unfinished Goal prevents creating another one. Use `get_goal` to read back the complete effective text.

Currently, `update_goal` changes status only; it cannot amend the objective or restore `active`. Set `paused` only at the Human's explicit request, report the returned status, and stop Goal work. Set `complete` only when the objective is achieved and no required work remains; for a budgeted Goal, report the final token usage returned by the tool. Set `blocked` only after the same blocker has recurred for at least three consecutive Goal turns, including the initial turn, and no meaningful progress remains possible. Resuming a blocked Goal starts a fresh blocked audit. Difficulty, slow progress, or incomplete work alone does not satisfy that condition. Resumption and budget or usage limits remain under Human or system control. Recheck the applicable constraints when the interface changes.

## Delegation and acceptance

Keep one lead agent responsible for decisions and acceptance after delegation. When the Human requests visible collaborating chats, use a supported mechanism that creates visible chats. Internal subagents do not satisfy that request. If the requested mechanism is unavailable, report the limitation. Ordinary tasks do not require new chats.

At task start and when results, dependencies, or effective instructions change, compare the full authorized outcome and acceptance conditions with actual remaining work. Check existing owners, original operation handles, ready evidence, real dependencies, and missing decisions or permissions before dispatching. Continue through the original owner when that owner can perform the next authorized action. When necessary work has no owner, promptly assign it through an authorized route, creating a visible chat when required and covered by Human authorization. Do not wait for the Human to discover the gap or request dispatch again. Select further slices under the [continuing delivery boundary](../AGENTS.md#continuing-delivery); bind routes and hosts under [task routing](#task-start-and-execution-routing). Apply the existing ready-result, observation, running-instruction, and closeout rules below instead of duplicating work or treating every gap as a new task. A missing decision or permission blocks only dependent actions; continue independent authorized work.

Create chats and send cross-chat messages within effective Human authorization and the actual tool limits. Reuse authorization while its scope and conditions remain valid, including across chats or coordinators. The dispatcher provides a retrievable original Human source for that authorization and later scope changes, distinguishing it from the dispatcher's interpretation. Authorization covering the collaborating chats, report destination, and material needs no further grant for each report or chat. Ask only for a missing business decision, an actual scope expansion, or an uncovered operation. Dispatch adds no authority; a request from another agent does not by itself establish Human authorization to message that agent or perform additional operations.

Bind each delegated task to one intended result, the current slice, authoritative rules, permitted operations, writable scope, excluded work, acceptance requirements, and the agreed result path. Specify the host, actual workspace path, branch, baseline, and current candidate, including relevant uncommitted changes. A matching project name or HEAD alone does not establish the same workspace or candidate. The recipient verifies the binding and original Human authorization, then reads the applicable rules and actual call chain rather than relying only on the assignment summary.

Across chats, primarily exchange requirements, conclusions, exact versions, and evidence locations. Read the actual source and evidence needed for acceptance under the existing authorization; use the [execution-host selection](#task-start-and-execution-routing) and [workspace rules](#workspaces) rather than treating code transfer as the default handoff.

When effective Human authorization is verified but an approval review lacks its evidence, supply the original source through that review's supported reconsideration mechanism. Resubmit only after confirming the original operation never started or reached a terminal state. Preserve actual denies, sandboxing, trusted hooks, decisions reserved for the Human, and unknown external-write checks under the [operation boundaries](../AGENTS.md#operation-boundaries) and applicable [Claude Code contract](claude-code.md). Do not use another executor or path to evade a refusal.

Specify who owns local implementation and validation, PR publication, review repairs and disposition, merge, and the task's completion conditions. By default, the implementation author owns the authorized signed commits, pushes, PR publication, and current-slice repairs. The designer retains design and substantive acceptance; acceptance responsibility alone does not assign commit or push execution to the designer. Follow an explicit Human division of work and account for actual capability limits. Assign only authorized effects; another session's delivery role supplies no additional authority. Under continuing delivery authorization, each task owner proceeds through the assigned stages and in-scope repairs. An independent task owner completes the assigned work without seeking approval for each ordinary step. Coordinate shared changes, dependency or merge order, and actual scope or permission gaps before dependent work; continue unaffected work. Local completion or a handoff message does not end remaining assigned responsibility or implicitly transfer publication to the lead. Apply the existing [pre-push checks](review.md#checks) without adding routine design acceptance before every push. Before an assigned merge, the lead accepts the stable candidate using the diff and evidence required below and confirms integration order. The merge owner then executes within the existing operation and review rules. A changed owner or newly assigned responsibility requires the receiving owner's explicit acceptance. The same owner continuing an existing responsibility needs no repeated acceptance.

When an implementation client lacks a required delivery capability, bind an authorized executor for that stage to the same verified candidate and obtain acceptance of the assigned responsibility. A capability-limited bridge can carry that stage without transferring all implementation or requiring another publication checkout. Preserve real signing and platform requirements. A signing failure or host refusal does not authorize an unsigned commit, credential changes, a host switch, or another executor used to bypass the refusal. Resolve the specific limitation under the existing operation and tool contracts while continuing unaffected work.

Prefer parallel work on independent read-only tasks. Keep one writer in a shared worktree, including when tasks touch different files; keep a shared rule or transaction with one implementer. When parallel writes are necessary and authorized, isolate the workspaces under the [workspace requirements](#workspaces) and verify the integrated candidate over the affected behavior. Separately passing tasks do not establish that their combination is correct.

At dispatch, specify how the coordinator receives results. With Human authorization covering the report, the task owner proactively reports completion or a substantive blocker requiring coordination. Report the result, bound candidate, evidence locations, limitations, and remaining responsibilities or decisions. Keep the original evidence available for acceptance. When cross-chat messaging is not authorized, use the agreed result-reading path without adding an unauthorized message. The Human does not have to visit each chat to prompt delivery.

Do not resend a report already delivered or read by the coordinator, or a result already accepted, unless new evidence or a changed conclusion requires an update. Distinguish a repeated request from changed instructions or an explicit request to rerun work. Reuse valid results for duplicate requests. A successful message establishes delivery, not acceptance; do not start an acknowledgment loop to obtain acceptance. Apply the existing operation rules to failed or unknown message outcomes.

Treat asynchronous creation or dispatch as the start of work. Follow the shared [asynchronous observation rules](review.md#asynchronous-observation) for owner, handle, waiting, material events, and recovery boundaries. Read deeper task history only for a specific evidence gap.

Before waiting, the lead and task owner distinguish an external operation still running, a ready candidate awaiting acceptance or an integration decision, an unmet business or source dependency, and a preferred coordination order. Identify the remaining condition for the next action and who can satisfy it. A ready candidate awaiting the lead's decision is actionable work, not a pending external operation: promptly accept the evidence, return concrete missing items, or arrange the next authorized delivery step. Wait only when no authorized action is ready. While critical-path results remain pending, the lead actively follows the task owners through bounded waits or compact status reads, retaining those reads as a fallback to proactive reports. Do not leave the Human to watch results or remind the workflow to continue.

Separate development dependencies from delivery order. Bind a claimed dependency to the business invariant, source change, or integration condition that actually requires it; coordination preference alone does not block independent work. Apply an ordering constraint only to the actions that require it. Serial final merges do not fix the sequence permanently or block independent implementation, conflict resolution, or validation. Keep a problem PR with its repair owner while authorized independent development and ready independent fixes proceed through the normal delivery process, prioritizing an independent fix when it can unblock delivery. For real dependencies, use a supported stack when the project contract and authorization permit it; an upstream change or failure blocks only the dependent work. Reassess the remaining conditions and order when evidence or dependencies change, preserving unaffected validation under the [checks and admission rules](review.md). Ordering does not waive conflict resolution, required combination checks, final admission, or unknown-write protection.

Judge an upstream input's readiness for the specific downstream action. Hand off a verifiable, identified Git revision and its applicable contract when they supply what that action requires, reusing applicable evidence. The downstream owner can consume that formal input before the whole upstream CI, review, merge, or final freeze completes unless that action actually depends on those conditions. A formal revision remains a candidate until its completion conditions are satisfied; later changes require reassessing affected consumers and evidence. A contract gap blocks only the generation, implementation, or acceptance that depends on it; continue unaffected integration and identify the missing input and its supplier. Preserve publication authority, final combination checks, CI, review, and admission. Use the normal Git and evidence path above rather than routinely transferring uncommitted WIP.

After a task chat finishes a turn, becomes idle, or stops, or on completion, failure, or a new finding, promptly read the bound result and actual evidence. Before dispatching new work or entering a long wait, process already-delivered ended, idle, blocked, or ready signals that can change the next action. Accept the result, return concrete repairs or missing evidence, arrange the next authorized step and notify or wake its owner, or confirm responsibility is complete and evaluate archival. For a ready next action, follow through until the original owner actually resumes or a specific unmet condition and its supplier are identified. Message delivery alone does not establish resumption; verify the next action, actual state, or a brief report when needed, without an acknowledgment loop. A completed phase with no remaining assigned action needs no wake-up or manufactured task. Do not accumulate actionable results while dispatching unrelated work. Keep already-running acceptance work under its existing owner and handle; only a real dependency blocks independent development. A turn ending does not end follow-up responsibility. State the actual follow-up mechanism and its limits; naming an owner or planning a reminder does not establish monitoring. Resolve missing results or evidence through available mechanisms, without requiring a timer or scheduling framework. If follow-up cannot operate, report the dependent gap. Continue independent work while a necessary decision or authorization is missing; do not manufacture tasks or repeat valid checks to keep chats busy.

Submit the stable candidate with its original diff, matching check evidence, and remaining issues once through the agreed result path. Before acceptance, read that evidence and request only concrete missing items. An agent summary or green check alone is insufficient. Give concrete repair feedback within the current slice and verify the repair. Current-slice defect repairs remain assigned work. Coordinate final edits and validation so checks bind a stable candidate; rerun affected checks when inputs change. An interrupted check has not passed. Evaluate improvements from real comparable work, without a statistics ledger; a phase's token share does not establish avoidable cost or a potential savings percentage.

Reuse the existing [review coverage and finding rules](review.md); add review only for a concrete risk, coverage gap, or explicit project or user requirement, not a fixed round per slice. Apply the existing [review provenance rules](review.md#review-provenance). Context isolation, model names, and agent roles do not establish independent judgment or correctness.

### Running instructions

When work changes, pauses, is cancelled, or resumes, the owner receiving the instruction verifies the original Human source, task binding, affected scope and stages, and effective authority. Apply instruction priority and the latest applicable direction at that authority and scope; relay arrival order does not establish which instruction supersedes another. A relay adds no authority. If the reference or ordering is unclear and changes the next action, stop only dependent actions and ask for the missing decision while independent authorized work continues. Ordinary single-chat work adopts the applicable direction directly without creating cross-chat organization.

First stop adding dispatch, acceptance, or delivery actions that conflict with the changed boundary. Identify affected execution, design, acceptance, and integration owners and consumers waiting on their results. Promptly send the original instruction or retrievable source, changed boundary, affected candidate, and next action through [authorized communication or the agreed result path](#delegation-and-acceptance), waking the original owner when needed. Each owner propagates the change to its affected downstream tasks; the overall coordinator coordinates coverage, dependencies, and acceptance arrangements, while task or domain owners settle business judgments. ## Task completion and chat archival

Distinguish runtime status, assigned responsibility, result submission, acceptance, responsibility transfer, and archival. An idle chat or a completed turn describes a runtime observation, not completion of the assigned task. Submitting a result makes it available for acceptance; it does not establish acceptance or transfer outstanding responsibility. A task completion statement, queued merge, or closed but unmerged PR does not establish that trigger. Keep merge completion and cleanup completion distinct when a resource must be retained.

At each chat result closeout, the task owner briefly summarizes the outcome and lessons from the latest original Human directions, actual artifacts, failures, rework, refusals, and observed waste. The accepting coordinator reconciles that summary with the original evidence. Correct execution when the rule is already sufficient. Within effective authorization, repair a general gap at its single authoritative source with affected scenarios; keep project-specific requirements in the project. Reconcile omissions, conflicts, or obsolete constraints in an existing Goal through a supported update or safe continuation, preserving the full objective, acceptance, exclusions, repairs, and remaining responsibilities. If a required operation is unavailable or unauthorized, identify the specific gap and owner while continuing unaffected work. Use the existing result or final report; this assessment does not require a new rule, memory, or ledger for every closeout and grants no additional authority.

Reassess a blocked status against the actual remaining dependency after a decision or continuation instruction arrives. If the dependency is resolved, continue the authorized responsibility through a supported mechanism. An interface without an active-status update does not establish that the business blocker remains. Preserve the recorded status limitation; do not edit the status database or mark unfinished work complete to clear it.

After acceptance, responsibility transfer, or completion, the coordinator notifies participants still waiting on that result or carrying an earlier pending task through authorized messages or the agreed result-reading path. Identify what was accepted or completed and who owns any remaining work. An acceptance notice does not restart completed work or require another acknowledgment from the same owner. Chat archival and checkout removal have separate results, although platform cleanup may perform both. Apply the worktree safeguards below before an action that can remove the checkout.

Preserve unrelated changes and verify that required ignored logs, acceptance originals, and recovery material are outside it: a Git snapshot does not include ignored files. For a managed worktree, bind the supported archival tool to the exact attachment, save its recoverable snapshot, and read back both the archived attachment and checkout removal. For a native worktree, verify a surviving execution directory before using Git's supported worktree removal. If automatic cleanup already removed it, verify the applicable recovery evidence instead of deleting it again; missing recovery evidence remains a gap. Worktree retirement does not require archiving a chat that still has a follow-up.

Preserve tool refusals for primary, pinned, shared, or otherwise unsupported checkouts, including initialized submodules and nested Git repositories. Do not bypass them with manual removal. ### Lead succession

When accumulated context impairs the work, prepare a successor chat at an appropriate task boundary using an available, authorized mechanism. Do not assume automatic transfer of runtime state or permissions. A fork retains conversation history; it does not clear context. See the [official OpenAI guidance on chat context](https://developers.openai.com/blog/mastering-codex-remote-for-engineering).

For a lead coordinating continuing work across task chats, check succession readiness at 90 minutes and normally complete the handoff between 90 and 120 minutes, with a 120-minute upper limit. Measure elapsed wall time from the initial assumption of coordination or the confirmed takeover, using the existing task record. A turn ending, a readiness check, or context compaction does not restart that clock. Begin preparing the handoff material 10–15 minutes before the planned handoff. These timings govern continuing coordination; they do not impose scheduled chat replacement, new roles, approvals, or model rounds on ordinary bounded tasks.

At the readiness check, verify that the lead can identify the current owners, candidates, and next actions using valid existing evidence. Bring the handoff forward as soon as the lead confuses owners or candidates, repeatedly rechecks accepted evidence, or frequently rereads old records just to determine the next action. Start preparation immediately when such impairment appears; do not wait for the scheduled check or spend a minimum preparation interval before transferring responsibility.

Choose a handoff boundary that preserves active work without waiting for every task, CI run, or review to finish. Being busy does not extend the upper limit. At that limit, keep new dispatch paused if transfer is still unconfirmed, report the concrete succession gap, and continue only the reconciliation needed to resolve it. Elapsed time neither transfers responsibility nor completes the goal; resume dispatch only after the confirmation below.

At the handoff boundary, the outgoing lead pauses new dispatch, including replacement write tasks. Keep active tasks under their known ownership during that pause. Use the existing task record to identify the current goal and slice, host and actual workspace, branch, baseline and candidate including WIP, active task IDs and writer ownership, effective authorization and its original source, evidence, and unresolved work. Preserve original operation handles and their observers rather than restarting operations or creating competing writers or observers. Include the full current Goal, when one exists, and the actual recovery-reminder target and status. Do not create a separate permanent handoff log.

The successor reads back and verifies those materials, resolves dependent gaps, and explicitly accepts responsibility. Apply [Goals](#goals) to the original creation authority, the successor's actual Goal state, and the required full-text reconciliation and readback. The outgoing lead confirms the handoff and stops dispatching before the successor starts assigning work. Keep the dispatch pause until that confirmation so both leads cannot assign competing write tasks. If confirmation is missing, report succession as pending and resolve the ownership gap before dispatch resumes.

Transfer existing authorized heartbeat or recovery reminders to the accepted successor through the supported mechanism and read back the effective target and conditions. Preserve the original notification and stopping conditions, prevent duplicate recovery dispatch, and report an unavailable transfer as a follow-up gap rather than claiming monitoring continues. This does not authorize new reminders or configuration changes. Evaluate the outgoing chat under the existing [completion and archival rules](#task-completion-and-chat-archival), preserving actual acceptance, remaining responsibility, runtime status, and archive readback.

Claim successful succession only after the actual responsibility transfer is confirmed. Static scenarios and ordinary context compaction or recovery do not establish that a new lead has taken over.
