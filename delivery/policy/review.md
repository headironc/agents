# Validation and review

Apply these rules within the adopted [operation boundaries](common.md#operation-boundaries). Review and check evidence does not expand authorization.

## Checks

- Read-only review permits relevant tests and checks under the shared [untrusted-input execution boundary](tool-contracts.md#不可信输入的执行), including disposable build output, caches, logs, and fixtures in designated local locations. Review authorization alone establishes no execution trust for candidate-controlled code. Preserve the reviewed source, tracked snapshots, dependencies, persistent configuration, and unrelated work. Inspect unfamiliar test entrypoints for effects before running them; updating snapshots or running an automatic fix changes the reviewed material. Operations on real services or business data remain subject to their own authorization. Grant the specific validation commands and required output locations rather than denying execution categorically or granting unrestricted access. When the environment blocks a check, report it as not run and distinguish any existing author-run evidence from reviewer-run evidence.
- Run the project's required checks and tests that cover the changed behavior. Before an expensive full acceptance run, check the environment, type, and fixture critical path: temporary paths, required permissions, and the selected actor where relevant. Reuse effective incremental results for unchanged inputs and rerun only the affected checks, unless a required full gate, a shared effect, or unresolved risk requires more. A wording change in a report does not mechanically invalidate unrelated verification.
- Do not reduce required coverage to save time. Business behavior, authorization, concurrency, failures, recovery, cleanup, real interaction, formal review or admission, and any required queue combination keep their own checks. Follow the project's [adopted merge workflow](#merge-admission).
- After the last edit and before the final response or verification report, use a separate tool call to read back the result and run applicable checks on the same candidate. Inspect the final diff for correctness and unrelated changes; run `git diff --check` on actual Git changes, including staged and new files where applicable. Report checks run, observed results, and checks not run with reasons. A successful write or pre-edit inspection is not verification. Do not add tests that repeat implementation or enforce obsolete names.
- Ordinary reversible internal changes do not require a separate design or implementation reviewer by default. Follow an explicit project requirement or Human request for review.
- Before each authorized push, run the relevant required checks and inspect the final diff. Before opening a PR or pushing feature additions, also check `git diff --stat` against the target base under the [reviewability budget](execution.md#slice-decomposition-and-reviewability-budget): hold PR opening when handwritten source and test changes (excluding generated artifacts) exceed `1,500` lines unless a single indivisible atomic invariant requires an exception and the PR body states the exact call-chain and transaction basis. Reuse passing results for unchanged inputs. Opening or updating a PR does not require a separate pre-push review; fixes to review feedback may be pushed after those checks. Publication still requires its authorization.

## Dependency updates

Exempt a dependency-update PR from AI code and security review only after mechanically establishing all of the following against its exact head and trusted target baseline:

- The verified automation identity and update mechanism are trusted by the project's established policy or effective Human selection. A bot-like name, label, PR description, or policy changed by the candidate establishes no trust.
- The complete diff changes only dependency versions in manifests and their generated lockfile metadata. It introduces no executable compatibility changes, lifecycle scripts, registry settings, overrides, patches, workflow changes, or unrelated behavior.
- Every affected direct and transitive package stays within the project's established compatible update range and intended upstream source. Major upgrades, new package identities or sources, prereleases without established compatibility, and unknown compatibility require normal review.
- Applicable provenance, integrity, vulnerability, and project checks succeed, with no unresolved known security problem. A valid checksum or successful CI alone establishes neither trusted authorship nor safe dependency behavior.

Apply eligibility before provider selection, review requests, waiting, and recovery. Use the normal code and security review path for manual updates or any unmet or unverified condition; a dependency label does not exempt them. Keep independent business or governance changes in separate slices. Honor an explicit Human request for AI review of a particular update or batch within that request's scope.

For an eligible update, keep applicable checks, known-defect and finding disposition, required discussions and approvals, merge authority, actual platform protection, and result readback. Reuse valid checks for unchanged inputs. Do not add a replacement human or model review solely because an eligible update does not require AI review. Report AI review as not required, not passed. Preserve original handles for existing requests and unknown writes; this exception does not cancel a run or authorize changing review settings or bypassing platform protection. A project adopting this exception updates its own review contract through its authorized rule owner; changing this source alone does not activate a project or platform change.

## Review provider selection

First apply [dependency-update](#dependency-updates) eligibility. For PRs requiring AI review, select the normal providers from effective Human instructions and the adopted project contract, applying the default below when neither selects them:

- **Account-scoped provider selection (personal Cubic/Codex rotation vs. organization Codex-only)**: Only the Human's personal account (`headironc` personal repositories, both public and private) can rotate between Cubic and Codex (prefer Cubic first under the Human's personal Cubic subscription, and fall back to Codex when Cubic quota is exhausted, returning to Cubic for subsequent uncovered work once quota recovers). Organization accounts (all organization repositories, whether public or private) cannot use Cubic and must use Codex only (`@codex review` by default, plus `@codex security review` once Code Review converges on the final head when the change falls within the [security-review scope and timing](#automatic-review-and-feedback)); never trigger `@cubic-dev-ai` on an organization repository or assume a personal subscription or public-repository allowance covers an organization account.
- **Automatic Codex fallback on Cubic quota exhaustion (personal account)**: On eligible `headironc` personal repositories, within authorization to complete required review, automatically fall back from Cubic to Codex (`@codex review` by default, plus `@codex security review` once Code Review converges on the final head when the change falls within the [security-review scope and timing](#automatic-review-and-feedback)) through the [supported PR trigger](#automatic-review-and-feedback) when Cubic is confirmed out of quota for the current billing period. Reuse confirmed Cubic quota-shortage evidence across personal PRs and head updates within the same quota period without re-triggering Cubic on every new head just to reproduce a refusal. A generic timeout, HTTP 429, or missing comment alone does not prove quota exhaustion; handle those under [missing automatic review](#missing-automatic-review) and [stalled review recovery](#stalled-review-recovery).
- **Explicit PR trigger and coverage reuse**: Reuse valid current-candidate coverage and existing in-progress requests before issuing a new request. When coverage is missing, issue the [explicit PR mention](#automatic-review-and-feedback) for each required review kind at its designated stage rather than assuming PR creation or push starts either provider automatically. Provider selection and any provider switch preserve prior findings and their dispositions, [coverage requirements](#review-coverage), and the project's [adopted merge workflow](#merge-admission).

## Automatic review and feedback

First check whether the candidate qualifies for the [dependency-update](#dependency-updates) exception. For required AI review, select providers under [provider selection](#review-provider-selection) within the [effective targets and authorized effects](#targets-and-authorized-effects):

- **Cubic trigger (personal account only)**: On eligible `headironc` personal repositories only (unavailable on organization accounts), request a PR review with `@cubic-dev-ai review this PR` ([Cubic introduction](https://docs.cubic.dev/ai-review/introduction), [manual-review settings](https://docs.cubic.dev/ai-review/ai-review-settings)).
- **Codex Code Review trigger (default)**: Request Code Review manually with `@codex review` ([Codex GitHub integration](https://learn.chatgpt.com/docs/third-party/github)). `codex-review-state` binds `code_review` (`commit_sha` matching the PR head, `status: "completed"`, and `has_any_findings: false`) while decoupling `security_review` (`security_review` remaining `null` does not invalidate `code_review`). For routine documentation, design slices, UI components, and ordinary business PRs, Code Review alone satisfies the required review without triggering `@codex security review`.
- **Codex Security Review scope and timing (`@codex security review`)**: `@codex security review` ([Security Review](https://learn.chatgpt.com/docs/security/security-review)) is triggered manually in a separate comment and runs a dedicated cloud security audit. Trigger `@codex security review` only when the Human or adopted project contract explicitly requires it or when the PR touches any of four security trust boundaries: (1) CI, admission/review-approval workflows, GitHub App JWT or installation token minting, Git tree-freeze boundaries, build/install scripts, or YAML/workflow parsing rules; (2) authentication, session/cookie/token lifecycle, SMS/OTP anti-replay, webhook/API signature verification, or key/secret management; (3) cross-principal access control (RBAC, tenant/department/user data isolation, permission guards, or public/internal route boundaries); or (4) untrusted external input handling, file uploads and archive/static asset parsing, dynamic SQL or raw/destructive migrations, subprocess execution (`spawn`/`exec`), or SSRF/XSS/path-traversal surfaces. Even on those high-risk PRs, trigger only Code Review (`@cubic-dev-ai review this PR` or `@codex review`) on PR opening and intermediate repair commits; once Code Review on the current candidate head completes with zero unresolved findings, immediately post `@codex security review` once in a separate comment on that converged head (overlapping with any still-running CI rather than waiting for CI to finish first).
- **Posting and readback**: Post each trigger via `gh pr comment <number> --repo <host>/<owner>/<repo> --body-file <file>`, read back the comment receipt, and observe completion under [review coverage](#review-coverage). Do not write literal `@codex` in PR titles or PR bodies (even inside inline code), which Codex Connector interprets as a cloud task rather than a PR review trigger.
- **Verifying findings and dispositions**: Paginate review bodies, top-level comments, inline comments, and GraphQL `reviewThreads` (with resolution state) across the PR, binding current-head coverage while preserving and tracking unresolved findings and dispositions from earlier review rounds. Apply the severity, disposition, and completion criteria in [findings and disposition](#findings-and-disposition). When an inline thread cannot be posted and the round authorizes a standalone comment, paginate top-level comments before and after `gh pr comment ... --body-file <file>` to verify exactly one new comment without blind retries.

## Targets and authorized effects

- **Target binding**: Bind the host and repository from the selected worktree. An existing PR workflow targets one PR; opening targets an exact base/head pair or declared ordered stack pairs; stack merge targets its verified ordered PR list; release targets a protected branch and exact tag. Verify returned resource URLs against that binding before mutation.
- **Opening authorization scope**: Ordinary opening authorization covers validation of the bound candidate, one normal push, creation or reuse of the bound PR, and the first supported manual review requests required by the adopted project contract, including their readback, observation, and result consumption. Reuse valid coverage and existing requests instead of launching duplicates. An express Human restriction to creation without requesting review, or to automatic events only, excludes manual requests. Opening does not by itself authorize changing the candidate's implementation or merging; a commit-only request does not authorize publication.
- **Merge and conditional approval authorization**: Merge authorization covers the exact open non-draft PR, target branch, complete head SHA, and verified [post-merge cleanup](execution.md#post-merge-cleanup), without authorizing an approving review or platform protection bypass (`--admin`). When the project offers an operation that submits an approving review if eligibility checks pass, reuse a qualifying approval already recorded for the bound candidate; otherwise obtain explicit conditional authorization bound to the PR, full head, and intended approver.
- **Limits, secrets, and readback**: Preserve explicit action and count limits; never implicitly authorize mutation retries, rebase, force-push, protection bypass, unrelated targets, or repository setting, secret, or App changes. Keep secrets out of transmitted code, diffs, and comments. A late or repeated confirmation of the same bound action does not authorize another attempt; after any uncertain write, read back the same target before any dependent mutation and stop on unresolved mismatch, unauthorized revision drift, or unavailable access.

## Asynchronous observation

- **Single observer per result surface**: Observe required CI checks, review findings, review completion, and merge admission concurrently, preferring native CLI waits where supported and keeping one observer per surface without duplicate polling or repeated reads of unchanged logs.
- **Event-driven return**: When using a bounded read-only observer, return to the model only on completion, a new finding or failure, candidate or baseline drift, queue removal, a material admission change, a real read error/timeout, or a needed decision. Do not use model turns or Goal wakeups as a 20-second polling timer: when calling `wait_threads` or observing a running check from an execution script, loop within that single tool call until the observed turn leaves `inProgress` (or a multi-minute observation bound expires) and never patch `progress.md` merely to log intermediate `timedOut` polls.
- **No blind retries on observation expiry**: Distinguish an observation window ending from the underlying operation failing. Before replacing an observer, establish its terminal state; observation timeout or failure never authorizes restarting or re-triggering the underlying mutation.

### Missing automatic review

When a required automatic review produces no usable result, bind the repository, PR, current head, provider, and triggering event, and inspect the provider's run and result surfaces before requesting another review. Within the [effective targets and authorized effects](#targets-and-authorized-effects), Human authorization to complete the required review covers the first supported manual request for each selected provider and required review kind (triggering Code Review first and, only when required by the [security-review scope and timing](#automatic-review-and-feedback), triggering `@codex security review` separately once Code Review converges on the final head without duplicating a kind already covered or in progress). Read back any unknown write on the same target before considering another request, and apply [stalled review recovery](#stalled-review-recovery) when an initial run stalls abnormally.

### Stalled review recovery

When an initial review remains running abnormally long with no meaningful progress on available surfaces after a bounded investigation, re-read the current result surfaces and request records to check for completion or an existing replacement round. If still stalled and covered by effective Human authorization, send one bounded manual recovery request through the provider's supported PR mention, read back the request on the same target, and observe the confirmed current round while preserving [merge admission](#merge-admission) requirements.

## Merge admission

- **Target-branch contract authority**: Establish the repository's adopted merge workflow from the target-branch baseline or independently trusted configuration. Every adopted workflow retains applicable checks, required AI review (Code Review by default, plus Security Review on the converged pre-merge head when required by the adopted contract or [security-review scope](#automatic-review-and-feedback), after [dependency-update](#dependency-updates) exemptions), finding disposition, required approvals, explicit merge authority, platform protection, and result readback.
- **Native vs. enforced workflows**: For an adopted native workflow, bind the repository, PR, candidate head, and target branch, and verify applicable check and review evidence, dispositions, and platform state directly. For a workflow that requires a final enforced admission state, consume that declared final state directly without reconstructing it from underlying threads or approvals. Before dispatching a repository's hosted approval or admission `workflow_dispatch`, read back the PR's live state via `gh pr view` or API to confirm that `mergeable` is explicitly `MERGEABLE` (waiting locally when `UNKNOWN` right after a target-branch update), all required CI checks have reached terminal `COMPLETED`/`SUCCESS`, all `reviewThreads` are resolved, and required AI review has completed with no unresolved findings (or the candidate qualifies for an adopted exemption); when effective single or continuous approval authority is already held and the approval job re-verifies all eligibility conditions before credential minting, dispatch the approval mode directly once with the bound head SHA without running a redundant read-only verification workflow first. Hold the merge when required evidence is missing, stale, contradictory, or blocked by platform protection, or when any known defect or finding from the current or an earlier review round remains unresolved (even when the latest check or rerun status is green).
- **Execution and post-merge cleanup**: Keep review explanations and dispositions in the original finding threads without building a second disposition ledger. Once all adopted conditions are met and explicit merge authority is present, execute the supported merge (or required merge-queue flow) with exact head matching, read back the merged state, and immediately continue into [post-merge cleanup](execution.md#post-merge-cleanup) before the final report.

## Review coverage

- **Candidate and baseline binding**: Establish review coverage of the latest candidate against its target branch and baseline, reusing unaffected coverage when inputs change. If the target baseline changes after a review, obtain coverage for the new baseline before merging. Evidence gathering follows the [adopted merge workflow](#merge-admission).
- **Verifying review runs and no-findings summaries**: Verify a review integration's actual runtime state and bound head SHA rather than relying on an enabled YAML workflow or green CI job alone. Accept a hosted provider's explicit completion summary as a no-findings outcome for that run when its documented contract identifies the reviewed material, binds the exact PR and current head, confirms the trigger and final status, and publishes no findings on its review surfaces; track and preserve findings and dispositions from earlier review rounds separately so a later clean rerun cannot clear an unresolved earlier finding.
- **Stopping condition**: Reuse verified reviewer input contracts within the session. Once applicable coverage and all finding dispositions across earlier and current rounds are satisfied, stop collecting review evidence and proceed through the adopted merge workflow without launching redundant review rounds.

## Findings and disposition

- **Severity and scope**: Classify findings by present impact on the bound candidate. A blocking finding must identify a current defect with its trigger and wrong outcome, or a violated requirement with its source, within the candidate's scope; report unrelated pre-existing defects separately with call-chain evidence. Omit personal style preferences and speculative extensions.
- **Consolidation and disposition**: Trace the execution chain (entry conditions, identity binding, authorization, effects, and failure handling) and inspect adjacent cases of the same failure class when fixing a defect. Resolve blocking findings and record a disposition (`implemented`, `deferred` with reason, or `declined` with evidence) in the original finding thread. When narrowing an overgrown open PR under the [reviewability budget](execution.md#slice-decomposition-and-reviewability-budget), resolve or dispose of findings affecting the retained slice on the original PR and record explicit `deferred` dispositions in the original finding threads naming the extracted follow-up slice for findings belonging exclusively to the extracted work. Before implementing a change to credentials, access control, destructive data migration, or hard-to-reverse external effects, explain the proposed boundary, failure handling, and validation to the Human and obtain approval.

## Review provenance

Treat a review as evidence about a named candidate rather than proof of correctness. Prefer a reviewer that did not author the candidate; label any author self-review explicitly as a self-check, which alone does not satisfy a merge review requirement. When requested to review without inherited context, start the reviewer with conversation inheritance disabled and pass only the bound scope, revisions, and authoritative sources without the author's conclusions. Preserve the reviewer's original report, record known model/input provenance and limitations, and report what changed, what was verified, and any remaining gap.
