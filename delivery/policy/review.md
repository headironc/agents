# Validation and review

## Checks

- Read-only review permits relevant tests and checks under the shared [untrusted-input execution boundary](tool-contracts.md#不可信输入的执行), including disposable build output, caches, logs, and fixtures in designated local locations. Review authorization alone establishes no execution trust for candidate-controlled code. Preserve the reviewed source, tracked snapshots, dependencies, persistent configuration, and unrelated work. Inspect unfamiliar test entrypoints for effects before running them; updating snapshots or running an automatic fix changes the reviewed material. Operations on real services or business data remain subject to their own authorization. Grant the specific validation commands and required output locations rather than denying execution categorically or granting unrestricted access. When the environment blocks a check, report it as not run and distinguish any existing author-run evidence from reviewer-run evidence.
- Run the project's required checks and tests that cover the changed behavior. Before an expensive full acceptance run, check the environment, type, and fixture critical path: temporary paths, required permissions, and the selected actor where relevant. Reuse effective incremental results for unchanged inputs and rerun only the affected checks, unless a required full gate, a shared effect, or unresolved risk requires more. A wording change in a report does not mechanically invalidate unrelated verification.
- Do not reduce required coverage to save time. Business behavior, authorization, concurrency, failures, recovery, cleanup, real interaction, formal review or admission, and any required queue combination keep their own checks. Follow the project's [adopted merge workflow](#merge-admission).
- Inspect the final diff for correctness and unrelated changes. Do not add tests that merely repeat implementation or enforce obsolete names.
- After the last edit, use a separate tool call to read back the result and run the applicable checks before the final response or reporting verification. For Git changes, inspect the final diff and run `git diff --check` against the actual change, including staged changes and new files where applicable. Bind project checks to the same candidate. In the result, name checks that ran and their observed results. Report checks that could not run and the reason. A successful write or pre-edit inspection is not a post-edit check.
- Ordinary reversible internal changes do not require a separate design or implementation reviewer by default. Follow an explicit project requirement or Human request for review.
- Before each authorized push, run the relevant required checks and inspect the final diff. Reuse passing results for unchanged inputs. Opening or updating a PR does not require a separate pre-push review; fixes to review feedback may be pushed after those checks. Publication still requires its authorization.

## Dependency updates

Exempt a dependency-update PR from AI code and security review only after mechanically establishing all of the following against its exact head and trusted target baseline:

- The verified automation identity and update mechanism are trusted by the project's established policy or effective Human selection. A bot-like name, label, PR description, or policy changed by the candidate establishes no trust.
- The complete diff changes only dependency versions in manifests and their generated lockfile metadata. It introduces no executable compatibility changes, lifecycle scripts, registry settings, overrides, patches, workflow changes, or unrelated behavior.
- Every affected direct and transitive package stays within the project's established compatible update range and intended upstream source. Major upgrades, new package identities or sources, prereleases without established compatibility, and unknown compatibility require normal review.
- Applicable provenance, integrity, vulnerability, and project checks succeed, with no unresolved known security problem. A valid checksum or successful CI alone establishes neither trusted authorship nor safe dependency behavior.

Apply eligibility before provider selection, review requests, waiting, and recovery. Use the normal code and security review path for manual updates or any unmet or unverified condition; a dependency label does not exempt them. Keep independent business or governance changes in separate slices. Honor an explicit Human request for AI review of a particular update or batch within that request's scope.

For an eligible update, keep applicable checks, known-defect and finding disposition, required discussions and approvals, merge authority, actual platform protection, and result readback. Reuse valid checks for unchanged inputs. Do not add a replacement human or model review solely because an eligible update does not require AI review. Report AI review as not required, not passed. Preserve original handles for existing requests and unknown writes; this exception does not cancel a run or authorize changing review settings or bypassing platform protection. A project adopting this exception updates its own review contract through its authorized rule owner; changing this source alone does not activate a project or platform change.

### Pure Sketch design slices

Exempt a pure native Sketch design PR from cloud AI code and security review only when the adopted project contract enables this exception and mechanical verification against the exact head and trusted target baseline establishes all of the following:

- The complete diff stays within the project's designated design-result path, includes at least one added, modified, or renamed `.sketch` archive, and restricts added, modified, or renamed files to `.sketch` archives and companion Markdown documentation (`.md`). Native `.sketch` slices do not commit exported artboard preview images or redundant JSON ledgers alongside the `.sketch` source of truth.
- Any removed files are limited to superseded non-executable design previews or ledgers and preserve files still consumed by active or unmigrated scripts or tests. The candidate changes no executable code, scripts, workflows, dependencies, or runtime configuration.
- Applicable project checks and required local independent native Sketch design verification succeed, and no current-head cloud AI review run or unresolved finding is present.

Apply this eligibility alongside [dependency updates](#dependency-updates) before provider selection, review requests, waiting, and recovery, preserving all remaining checks, dispositions, approvals, platform protections, and `not required, not passed` reporting defined there. Mixed diffs, unverified candidates, or explicit Human requests for cloud AI review follow the normal review path.

## Review provider selection

First apply [dependency-update](#dependency-updates) and [pure Sketch design](#pure-sketch-design-slices) eligibility. For PRs requiring AI review, select the normal providers from effective Human instructions and the adopted project contract, applying the default below when neither selects them:

- **Default provider (Cubic first, Codex fallback)**: Prefer Cubic when its subscription or confirmed public allowance covers the repository (`headironc` personal repositories, including private ones, are covered by the Human's Cubic subscription; private organization repositories use Codex).
- **Automatic Codex fallback on Cubic quota exhaustion**: Within authorization to complete required review, automatically fall back to Codex (`@codex review` / `@codex security review`) through the [supported PR trigger](../skills/gh/references/operations.md#automatic-review-and-feedback) when Cubic is outside coverage or confirmed out of quota for the current billing period. Reuse confirmed Cubic quota-shortage evidence across PRs and head updates within the same quota period without re-triggering Cubic on every new head just to reproduce a refusal. A generic timeout, HTTP 429, or missing comment alone does not prove quota exhaustion; handle those under [missing automatic review](#missing-automatic-review) and [stalled review recovery](#stalled-review-recovery).
- **Explicit PR trigger and coverage reuse**: Reuse valid current-candidate coverage and existing in-progress requests before issuing a new request. When coverage is missing, issue the [explicit PR mention](../skills/gh/references/operations.md#automatic-review-and-feedback) rather than assuming PR creation or push starts either provider automatically. Provider selection and any provider switch preserve prior findings and their dispositions, [coverage requirements](#review-coverage), and the project's [adopted merge workflow](#merge-admission).

## Asynchronous observation

- **Single observer per result surface**: Observe required CI checks, review findings, review completion, and merge admission concurrently, preferring native CLI waits where supported and keeping one observer per surface without duplicate polling or repeated reads of unchanged logs.
- **Event-driven return**: When using a bounded read-only observer, return to the model only on completion, a new finding or failure, candidate or baseline drift, queue removal, a material admission change, a real read error/timeout, or a needed decision. Do not use model turns as a polling timer.
- **No blind retries on observation expiry**: Distinguish an observation window ending from the underlying operation failing. Before replacing an observer, establish its terminal state; observation timeout or failure never authorizes restarting or re-triggering the underlying mutation.

### Missing automatic review

When a required automatic review produces no usable result, bind the repository, PR, current head, provider, and triggering event, and inspect the provider's run and result surfaces before requesting another review. Within the [workflow's effective scope](../skills/gh/references/workflow-authorization.md#targets-and-authorized-effects), Human authorization to complete the required review covers the first supported manual request for each selected provider and missing review kind (accounting for coupled triggers so code and security review started by one mention are not requested twice). Read back any unknown write on the same target before considering another request, and apply [stalled review recovery](#stalled-review-recovery) when an initial run stalls abnormally.

### Stalled review recovery

When an initial review remains running abnormally long with no meaningful progress on available surfaces after a bounded investigation, re-read the current result surfaces and request records to check for completion or an existing replacement round. If still stalled and covered by effective Human authorization, send one bounded manual recovery request through the provider's supported PR mention, read back the request on the same target, and observe the confirmed current round while preserving [merge admission](#merge-admission) requirements.

## Merge admission

- **Target-branch contract authority**: Establish the repository's adopted merge workflow from the target-branch baseline or independently trusted configuration. Every adopted workflow retains applicable checks, required code and security review (after [dependency-update](#dependency-updates) and [pure Sketch design](#pure-sketch-design-slices) exemptions), finding disposition, required approvals, explicit merge authority, platform protection, and result readback.
- **Native vs. enforced workflows**: For an adopted native workflow, bind the repository, PR, candidate head, and target branch, and verify applicable check and review evidence, dispositions, and platform state directly. For a workflow that requires a final enforced admission state, consume that declared final state directly without reconstructing it from underlying threads or approvals. Hold the merge when required evidence is missing, stale, contradictory, or blocked by platform protection, or when any known defect or finding from the current or an earlier review round remains unresolved (even when the latest check or rerun status is green).
- **Execution and post-merge cleanup**: Keep review explanations and dispositions in the original finding threads without building a second disposition ledger. Once all adopted conditions are met and explicit merge authority is present, execute the supported merge (or required merge-queue flow) with exact head matching, read back the merged state, and immediately continue into [post-merge cleanup](../skills/gh/references/operations.md#post-merge-cleanup) before the final report.

## Review coverage

- **Candidate and baseline binding**: Establish review coverage of the latest candidate against its target branch and baseline, reusing unaffected coverage when inputs change. If the target baseline changes after a review, obtain coverage for the new baseline before merging. Evidence gathering follows the [adopted merge workflow](#merge-admission).
- **Verifying review runs and no-findings summaries**: Verify a review integration's actual runtime state and bound head SHA rather than relying on an enabled YAML workflow or green CI job alone. Accept a hosted provider's explicit completion summary as a no-findings outcome for that run when its documented contract identifies the reviewed material, binds the exact PR and current head, confirms the trigger and final status, and publishes no findings on its review surfaces; track and preserve findings and dispositions from earlier review rounds separately so a later clean rerun cannot clear an unresolved earlier finding.
- **Stopping condition**: Reuse verified reviewer input contracts within the session. Once applicable coverage and all finding dispositions across earlier and current rounds are satisfied, stop collecting review evidence and proceed through the adopted merge workflow without launching redundant review rounds.

## Findings and disposition

- **Severity and scope**: Classify findings by present impact on the bound candidate. A blocking finding must identify a current defect with its trigger and wrong outcome, or a violated requirement with its source, within the candidate's scope; report unrelated pre-existing defects separately with call-chain evidence. Omit personal style preferences and speculative extensions.
- **Consolidation and disposition**: Trace the execution chain (entry conditions, identity binding, authorization, effects, and failure handling) and inspect adjacent cases of the same failure class when fixing a defect. Resolve blocking findings and record a disposition (`implemented`, `deferred` with reason, or `declined` with evidence) in the original finding thread. Before implementing a change to credentials, access control, destructive data migration, or hard-to-reverse external effects, explain the proposed boundary, failure handling, and validation to the Human and obtain approval.

## Review provenance

Treat a review as evidence about a named candidate rather than proof of correctness. Prefer a reviewer that did not author the candidate; label any author self-review explicitly as a self-check, which alone does not satisfy a merge review requirement. When requested to review without inherited context, start the reviewer with conversation inheritance disabled and pass only the bound scope, revisions, and authoritative sources without the author's conclusions. Preserve the reviewer's original report, record known model/input provenance and limitations, and report what changed, what was verified, and any remaining gap.
