# GitHub operations

Read the [GitHub CLI contract](../SKILL.md). Use tool `gh` for the operation actually requested. Read the [Git transport rules](../../../policy/tool-contracts.md#git). Use tool `git` only within the same authorized target and action limits.

## Identity and authorization

Before a named operation, read this skill's [workflow authorization](workflow-authorization.md). Use the installed `gh-identity` skill and its `references/auth-readiness.md` for identity selection and credential recovery. Resolve references from each skill's physical directory. Preserve the workflow's target, authorized effects and limits; command examples grant no additional authority.

Every operation uses `headironc`. Follow the Git transport rules for the HTTPS default, credential helper and target access checks. A GitHub API identity alone does not prove which credentials Git uses or establish push permission. Verify the actual transport before its write; require SSH identity evidence only when the operation uses SSH. After an identity failure, stop and report it; do not select another account or credential source.

## Open or reuse a PR

Bind the host/repository and exact base/head pair before any mutation. Apply the [opening authorization boundary](workflow-authorization.md#targets-and-authorized-effects) to preparation, implementation changes, and signed commits. Publishing an existing candidate does not grant implementation authority. Preserve the one normal push and one create-or-reuse limit. A commit-only request does not authorize publication.

Require a feature branch, a clean committed candidate, matching final diff and required validation. Verify the remote's effective URLs, fetch successfully, and establish the intended base without updating another workspace. All commits must belong to the change or a declared dependency.

Create new PRs ready for review by default. Use a draft only when the user requests it or an explicit project requirement calls for it. Preserve an existing PR's draft state when reusing it unless a state change is authorized. Missing reviewer configuration or review results does not justify creating or reverting a draft.

Query the exact head before pushing. Reuse only one open PR with the intended base, head, title, repository and human author; conflicting matches block the operation. Verify its head SHA, not merely the branch name. Establish the exact upstream if absent, then use one normal push with an explicit refspec. Read the remote ref back and require the intended object ID.

When no matching PR exists, create with the explicit repository, base, head, title and body file. Apply the [writing conventions](../../../policy/writing.md). Read back number, URL, state, draft status, author, base and exact head. A failed or timed-out creation is not permission to create again: query the exact head once and verify exactly one matching result, otherwise report an unknown outcome and stop. A failed or unknown push likewise requires readback, never an automatic retry.

After PR readback, continue to [required review requests](#automatic-review-and-feedback) under the [opening scope](workflow-authorization.md#targets-and-authorized-effects). Before reporting the opening workflow complete, consume valid coverage, follow an existing request, issue the missing authorized first request, or report its specific scope or capability gap. A created PR and green CI alone do not complete that review step.

## Automatic review and feedback

First check whether the candidate qualifies for the shared [dependency-update](../../../policy/review.md#dependency-updates) exception. For required AI review, apply [automatic-review authorization and waiting](workflow-authorization.md#automatic-review-and-waiting) and select providers under [provider selection](../../../policy/review.md#review-provider-selection) within the [effective opening or review-completion scope](workflow-authorization.md#targets-and-authorized-effects):

- **Cubic trigger**: Request a PR review with `@cubic-dev-ai review this PR` ([Cubic introduction](https://docs.cubic.dev/ai-review/introduction), [manual-review settings](https://docs.cubic.dev/ai-review/ai-review-settings)).
- **Codex Code Review trigger (default)**: Request Code Review manually with `@codex review` ([Codex GitHub integration](https://learn.chatgpt.com/docs/third-party/github)). `codex-review-state` binds `code_review` (`commit_sha` matching the PR head, `status: "completed"`, and `has_any_findings: false`) while decoupling `security_review` (`security_review` remaining `null` does not invalidate `code_review`). For routine documentation, design slices, and ordinary business PRs, `@codex review` alone satisfies the Codex review requirement without triggering `@codex security review`.
- **Codex Security Review scope and timing (`@codex security review`)**: `@codex security review` ([Security Review](https://learn.chatgpt.com/docs/security/security-review)) is triggered manually in a separate comment, takes 8–15 minutes per run, and consumes separate Codex cloud review quota. Trigger `@codex security review` only when the Human or adopted project contract explicitly requires it or when the PR touches security trust boundaries: (1) CI, admission/review-approval workflows, GitHub App JWT or installation token minting, Git tree-freeze boundaries, or YAML/workflow parsing rules; (2) authentication, session/cookie/token lifecycle, SMS/OTP anti-replay, webhook signature verification, or key/secret management; (3) cross-principal access control (RBAC, tenant/department data isolation, permission guards, or public/internal route isolation); or (4) high-risk untrusted external input handling, file uploads and static asset parsing, dynamic SQL or raw migrations, subprocess execution (`spawn`/`exec`), or SSRF/XSS/path-traversal surfaces. Even on those high-risk PRs, run `@codex review` (or Cubic) first to converge code logic, boundary conditions, and CI checks, then post `@codex security review` once in a separate comment on the converged pre-merge candidate head right before merge admission (never alongside the initial `@codex review` or on every intermediate repair commit).
- **Posting and readback**: Post each trigger via `gh pr comment <number> --repo <host>/<owner>/<repo> --body-file <file>`, read back the comment receipt, and observe completion under the installed [shared review rules](../../../policy/review.md#review-coverage). Do not write literal `@codex` in PR titles or PR bodies (even inside inline code), which Codex Connector interprets as a cloud task rather than a PR review trigger.
- **Verifying findings and dispositions**: Paginate review bodies, top-level comments, inline comments, and GraphQL `reviewThreads` (with resolution state) across the PR, binding current-head coverage while preserving and tracking unresolved findings and dispositions from earlier review rounds. Apply the severity, disposition, and completion criteria in [review rules](../../../policy/review.md) and the [repair scope and round boundaries](workflow-authorization.md#review-fixes). When an inline thread cannot be posted and the round authorizes a standalone comment, paginate top-level comments before and after `gh pr comment ... --body-file <file>` to verify exactly one new comment without blind retries.

## Merge

Require explicit authority for the exact PR, open non-draft state, target branch, and complete head SHA. Verify the project's adopted workflow under [shared merge admission](../../../policy/review.md#merge-admission) (either direct check/review/disposition verification for a native workflow or reading the declared final admission state when required). When the adopted workflow dispatches a hosted approval `workflow_dispatch`, first verify via local PR readback (`gh pr view`) that `mergeable` is `MERGEABLE` (polling locally if `UNKNOWN` after a recent base advance), required CI checks are `COMPLETED`/`SUCCESS`, all `reviewThreads` are resolved, and required AI review has completed or is exempted; when approval authority is already held and the approval job re-verifies eligibility before minting credentials, dispatch the approval mode directly once with the bound head SHA rather than running a redundant read-only verification workflow first. When satisfied, execute ordinary squash merge or the target branch's required queue flow with exact head matching (never `--admin` or protection bypass), read back the merged state, and immediately continue into [post-merge cleanup](#post-merge-cleanup) before the final report.

### Post-merge cleanup

Confirmed merge readback immediately triggers cleanup under the existing [merge authorization](workflow-authorization.md#targets-and-authorized-effects):

- **Primary checkout on a feature branch (solo default)**: When the clean primary checkout is owned by this task and bound to the merged feature branch, switch back to a verified safe branch (such as `main`) without touching unrelated worktrees.
- **Dedicated task worktree**: If an isolated worktree was allocated for this PR and its HEAD matches the merged PR head with no remaining consumers or uncommitted changes, preserve any needed ignored evidence outside it and retire the worktree through the client's archival tool or `git worktree remove`. When a coordinator merges a delegated worker slice (or retires a superseded helper worker) with no remaining responsibility or in-flight operation on that worker chat, atomically retire the worker's worktree, archive the completed worker chat (`set_thread_archived` with `archived: true`), and remove the entry from the active `progress.md` table before advancing the slot. Never force-remove primary, pinned, or shared checkouts.
- **Branch removal and readback**: Once no worktree uses the local branch and its tip equals the merged PR head, delete the local branch and delete the remote head ref while it still points to that head. Read back worktree and ref states and report the merged PR and cleanup results separately.

## Native stacks

Bind the exact ordered parent/head pairs and selected remote. Validate each layer against its actual parent. Publish bottom-up, with one normal push and create-or-reuse readback per declared layer. Stop later layers after a failure. Apply the automatic-review boundary separately to each event and resulting head.

Link only already-created PR numbers or explicit URLs using the installed `gh stack link` syntax and explicit remote. Branch arguments can push/create implicitly and are not admitted here. Verify the stack number, size, positions, ordered PRs, bases, heads and repository after linking. Do not substitute `stack submit`, `stack add`, or an extension for missing native capability.

Alignment is a separately authorized history rewrite and publication; opening or review alone does not authorize it. Merge requires authority for the exact complete stack, satisfaction of the adopted workflow for every layer under [Merge](#merge), and a compatible native complete-stack squash invocation. Do not silently merge a prefix or one layer at a time. Confirm all members merged before deleting any stack branch.

## Release

Use explicit release authority, the verified protected branch and exact tag. Require a clean committed source matching the successfully fetched remote base and no existing tag/release collision. Use the Human's version; if absent, the retained personal convention is the next patch of the latest stable semantic release, or `v0.0.1` when none exists. Bind it before creation, not from commit messages. Create once with scoped release notes, then verify tag, target commit and URL. An uncertain outcome requires readback; do not rewrite tags, force-push or create source commits as part of releasing.
