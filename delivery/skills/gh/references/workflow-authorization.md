# GitHub workflow authorization

Read this contract before preparing a named GitHub workflow or making its first external request. Bind the user's request and existing authorization to the target and permitted effects. This contract records those boundaries; it does not grant permission or launch a workflow. Use [operations](operations.md) for execution and [authentication readiness](auth-readiness.md) for identity preparation.

## Targets and authorized effects

- Bind the host and repository from the selected worktree. An existing PR workflow targets one PR; opening targets an exact base/head pair or declared ordered stack pairs; stack merge targets its verified ordered PR list; release targets a protected branch and exact tag. Verify returned resource URLs against that binding before mutation.
- Resolve ordinary technical details from the request and verified context. Recording branch names, commit IDs, diff hashes, and permitted actions carries out existing authorization; it does not require another business decision.
- Ordinary opening authorization covers validation of the bound candidate, one normal push, creation or reuse of the bound PR, and the first supported manual review requests required by the adopted project contract, including their readback, observation, and result consumption. Reuse valid coverage and existing requests instead of launching duplicates. An express Human restriction to creation without requesting review, or to automatic events only, excludes manual requests. Opening does not by itself authorize changing the candidate's implementation. Feature-branch preparation, implementation changes, and signed commits are included only when the request or existing session authorization also covers those actions, within that scope and any stated commit limits. Reuse such authorization without asking again. A commit-only request does not authorize publication. Review findings retain their own repair and disposition authority below; opening or fixing does not authorize merge.
- Merge authorization covers the exact PR and its verified cleanup. It does not authorize submitting an approving review. The repository's adopted merge workflow remains required under the [shared rules](../../../policy/review.md#merge-admission), including any explicitly required platform enforcement.
- When the project offers an operation that submits an approving review if eligibility checks pass, distinguish it from a read-only check. Reuse a qualifying approval already recorded for the bound candidate. When write authority is missing, present the bound PR, full head, and intended approver, and ask for the actual effect: “Verify eligibility and, if it passes, submit one approving review.” One explicit conditional authorization can cover both steps when the adopted workflow permits it. Preserve any project-required evidence, action-time confirmation, and supported approval route.
- Identity selection and the read-only target, revision, check, review, and run queries needed for the authorized operation require no additional business decision.
- Preserve explicit action and count limits. A workflow never implicitly authorizes a mutation retry, rebase, force-push, protection bypass, unrelated target, repository setting or secret change, or App installation. Credential recovery remains governed by [authentication readiness](auth-readiness.md).
- Sending ordinary repository code, diffs and review context as part of an authorized workflow needs no separate approval. Keep secrets and sensitive data out of transmitted material; remove or redact them before sending.
- A late or repeated confirmation of the same bound action does not authorize another attempt. Reuse a confirmed result or follow the original operation while it is in progress. After an uncertain write, read back the same target before any dependent mutation. Do not repeat the write automatically. Stop dependent work on unresolved identity or target mismatch, unauthorized revision change, unavailable access, or an unverified write outcome.

## Review fixes

- Distinguish a request limited to named findings from a request to repair a PR within a stated implementation scope. The first admits only those findings and their authorized dispositions. The second also admits newly discovered defects and repair regressions within that scope. Finding severity or a new finding ID alone does not invalidate existing authorization.
- Before dependent work, seek a decision only for a missing business choice, an effect outside the authorized scope, an exhausted explicit action limit, or a design approval required by the shared rules. Explain the exact boundary. Continue independent authorized work.
- Bind each repair round to the exact PR, observed head, permitted fixes, commit and push limits, replies, and thread resolutions. A bounded round uses zero or one signed atomic commit and at most one normal push. Under continuing authorization for the repair scope and publication, further rounds may proceed without renewed approval; retain all prior writes and any user-specified cumulative limits.
- A read-only observation does not authorize a repair, reply, or resolution. When existing authorization does cover those actions, transition to the repair round without asking again. Reporting a suggestion alone grants no authority to implement or dispose of it.
- Before pushing, bind the resulting commit, its parent, final diff, and validation to the round's observed head. After push readback, bind the exact resulting PR head before replies or resolutions. A disposition-only round remains bound to the observed head. An unrelated head transition requires reassessment, not an automatic overwrite.
- Keep the round active through its authorized writes, readback, required review verification, and finding disposition. Reuse unchanged coverage and dispositions, including valid project gate evidence under the shared rules. New in-scope findings continue under remaining authorization, while an out-of-scope finding blocks only its dependent work.
- Replies and resolutions require disposition authority. A round may authorize at most one standalone disposition comment per named finding whose inline thread could not be posted. Follow the operation reference's exact comment readback and no-retry rules.
- If only non-blocking threads without disposition authority remain, report their IDs, locations, and needed decisions. End the round with disposition pending; do not relabel that missing decision as a code defect or poll unchanged results again.

## Workflow scope and host permissions

- Establish or reuse a scope record for the fixed identity, host, repository, target, and allowed reads, writes, readback, and cleanup. Preserve it across handoffs. It is an agent-maintained boundary, not a host-enforced grant and not a requirement to create a separate ledger for ordinary work.
- Before PR creation, PR access is limited to exact-head discovery and create or reuse. Bind the one resulting PR number, URL, base, and head from readback before further PR-specific operations. For a stack, do this for each declared pair.
- Keep actual host permission evidence separate. Obtain the required bounded host grant when necessary; existing host access alone is not business authorization. Do not substitute generic command prefixes for a scoped grant or change host policy to proceed.
- Identity readiness may use only the literal host and profile selected for this workflow and the status, selection, identity-query, and permitted recovery procedures in [authentication readiness](auth-readiness.md). Those operations neither select a repository nor authorize its mutation.
