# GitHub workflow authorization

Read this contract before preparing a named GitHub workflow or making its first external request. Bind the user's request and existing authorization to the target and permitted effects. This contract records those boundaries; it does not grant permission or launch a workflow. Use [operations](operations.md) for execution and the installed `gh-identity` skill for authentication.

## Targets and authorized effects

- Bind the host and repository from the selected worktree. An existing PR workflow targets one PR; opening targets an exact base/head pair or declared ordered stack pairs; stack merge targets its verified ordered PR list; release targets a protected branch and exact tag. Verify returned resource URLs against that binding before mutation.
- Resolve ordinary technical details from the request and verified context. Recording branch names, commit IDs, diff hashes, and permitted actions carries out existing authorization; it does not require another business decision.
- Opening authorization covers validation of the bound candidate, one normal push, and creation or reuse of the bound PR. It does not by itself authorize changing the candidate's implementation. Feature-branch preparation, implementation changes, and signed commits are included only when the request or existing session authorization also covers those actions, within that scope and any stated commit limits. Reuse such authorization without asking again. A commit-only request does not authorize publication. Opening or fixing does not authorize merge.
- Merge authorization covers the exact PR and its verified cleanup. It does not authorize submitting an approving review. The repository's adopted merge workflow remains required under the [shared rules](../../../policy/review.md#merge-admission), including any explicitly required platform enforcement.
- Identity selection and the read-only target, revision, check, review, and run queries needed for the authorized operation require no additional business decision.
- Preserve explicit action and count limits. A workflow never implicitly authorizes a mutation retry, rebase, force-push, protection bypass, unrelated target, repository setting or secret change, or App installation. Credential recovery remains governed by the identity skill.
- Sending ordinary repository code, diffs and review context as part of an authorized workflow needs no separate approval. Keep secrets and sensitive data out of transmitted material; remove or redact them before sending.
- After an uncertain write, read back the same target before any dependent mutation. Do not repeat the write automatically. Stop dependent work on unresolved identity or target mismatch, unauthorized revision change, unavailable access, or an unverified write outcome.

## Review fixes

- Distinguish a request limited to named findings from a request to repair a PR within a stated implementation scope. The first admits only those findings and their authorized dispositions. The second also admits newly discovered defects and repair regressions within that scope. Finding severity or a new finding ID alone does not invalidate existing authorization.
- Before dependent work, seek a decision only for a missing business choice, an effect outside the authorized scope, an exhausted explicit action limit, or a design approval required by the shared rules. Explain the exact boundary. Continue independent authorized work.
- Bind each repair round to the exact PR, observed head, permitted fixes, commit and push limits, replies, and thread resolutions. A bounded round uses zero or one signed atomic commit and at most one normal push. Under continuing authorization for the repair scope and publication, further rounds may proceed without renewed approval; retain all prior writes and any user-specified cumulative limits.
- A read-only observation does not authorize a repair, reply, or resolution. When existing authorization does cover those actions, transition to the repair round without asking again. Reporting a suggestion alone grants no authority to implement or dispose of it.
- Before pushing, bind the resulting commit, its parent, final diff, and validation to the round's observed head. After push readback, bind the exact resulting PR head before replies or resolutions. A disposition-only round remains bound to the observed head. An unrelated head transition requires reassessment, not an automatic overwrite.
- Keep the round active through its authorized writes, readback, required review verification, and finding disposition. Reuse unchanged coverage and dispositions, including valid project gate evidence under the shared rules. New in-scope findings continue under remaining authorization, while an out-of-scope finding blocks only its dependent work.
- Replies and resolutions require disposition authority. A round may authorize at most one standalone disposition comment per named finding whose inline thread could not be posted. Follow the operation reference's exact comment readback and no-retry rules.
- If only non-blocking threads without disposition authority remain, report their IDs, locations, and needed decisions. End the round with disposition pending; do not relabel that missing decision as a code defect or poll unchanged results again.

## Automatic review and waiting

- An authorized PR creation, ready transition or repair push includes automatic reviews triggered by that event under the existing repository configuration.
- Follow the installed [shared review coverage rules](../../../policy/review.md#review-coverage) and [operation contract](operations.md#automatic-review-and-feedback) for review work and finding disposition. Missing configuration or review evidence does not block an otherwise authorized PR creation, ready transition or repair push. Merge work follows the adopted workflow under [Merge](operations.md#merge); native review evidence supplies its declared conditions, while required enforcement cannot be replaced by a manual fallback.
- For direct verification, follow the actual provider's input and result contract. A repository workflow exposes workflow and Action revisions, permissions, and configured model or prompt inputs; bind the applicable fields. A hosted App may expose its verified identity, documented scope, trigger, and completion summary instead. Record unavailable internals as unknown; do not demand another provider's artifacts or invent a workflow for an App.
- Automatic-event authority alone does not authorize a local reviewer CLI, manual trigger, retry, or additional launch for the same provider, resulting head, and event. When effective Human authorization covers completing the required review, apply [provider selection and explicit PR requests](../../../policy/review.md#review-provider-selection), the [first-request authorization and readback rules](../../../policy/review.md#missing-automatic-review), and [stalled review recovery](../../../policy/review.md#stalled-review-recovery) only when an existing run is stalled. A planned first mention does not require an automatic failure first. Preserve narrower event-only or one-time authorization.
- Read back the evidence required by the selected path. Reuse applicable verified contracts and unaffected evidence under the shared rules. Once coverage and dispositions satisfy those rules, stop review verification and continue the authorized operation; do not wait for another report or repeat covered evidence checks.
- Follow the shared [asynchronous observation rules](../../../policy/review.md#asynchronous-observation) for result-surface coverage, concurrent waiting, intervals, and observer recovery. Inspect the installed command's help before selecting a native watch; a check watcher does not necessarily observe a provider's findings or review-summary comments. Use the provider's actual result surfaces for review observation.
- Stop the affected wait on cancellation, target drift, unavailable access, or unrecoverable run identity. Extend a Human-specified total wait limit only with their decision. A final admission state does not require identifying or waiting for underlying runs again. Continuing queries never authorizes resubmitting a mutation.

## Workflow scope and host permissions

- Establish or reuse a scope record for the fixed identity, host, repository, target, and allowed reads, writes, readback, and cleanup. Preserve it across handoffs. It is an agent-maintained boundary, not a host-enforced grant and not a requirement to create a separate ledger for ordinary work.
- Before PR creation, PR access is limited to exact-head discovery and create or reuse. Bind the one resulting PR number, URL, base, and head from readback before further PR-specific operations. For a stack, do this for each declared pair.
- Keep actual host permission evidence separate. Obtain the required bounded host grant when necessary; existing host access alone is not business authorization. Do not substitute generic command prefixes for a scoped grant or change host policy to proceed.
- Identity readiness may use only the literal host and profile selected for this workflow and the identity skill's status, selection, identity-query, and permitted recovery procedures. Those operations neither select a repository nor authorize its mutation.
